## 3. Kitchen 전역 장면 평가 (54/54) — 렌더링 버그 근본 수정

### 3-1. 원인 진단 정정 이력 (정직하게 기록)

- **최초(2026-09-16) 진단**: "파트가 1개(handle)뿐인 물체에 대해 모델이 유효 범위 밖의 parent
  인덱스를 예측했다"고 결론 내리고, 크래시 나는 3개 장면(28/34/48)을 try/except로 격리해 51/54로
  완주율만 확보했다.
- **2026-09-17 재조사에서 이 진단이 틀렸음을 발견**: 실제로 고쳐보려고 `visualization_parts()`에
  디버그 프린트를 심어 흐름을 추적한 결과, 문제의 물체는 파트가 **2개**(mesh=`[0,4]`)였다. 첫
  번째 파트(mesh=0="none", 유효하지 않은 파트)가 렌더링 코드에서 조용히 건너뛰어지면서
  `write_urdfs()`가 만드는 `link_names`가 2칸(`['base_link','handle0']`)으로 압축됐는데, 두 번째
  파트(handle)의 parent 참조값(`2`, 압축 전 번호 체계 기준으로는 유효)이 압축 후 목록 범위를
  벗어나 크래시가 난 것이었다. "파트 1개짜리"라는 최초 진단은 크래시 시점의 겉보기 증상만 보고
  내린 부정확한 결론이었다.
- **근본 수정**: 실제로 링크가 만들어진 원본 인덱스만 순서대로 다시 번호를 매기는 매핑
  (`old_to_new_idx`)을 추가하고, 각 파트의 parent 참조를 이 매핑으로 변환하도록 `utils.py`를
  수정(매핑에 없는 값은 base_link로 폴백). 예측값(mesh/position 등) 자체는 바꾸지 않았다.
- **검증**: 28/34/48 개별 재현 → 전부 성공. 54개 전체 재실행 → **54/54 전부 성공**. `test28.png`
  직접 열람 확인 — 캐비닛+가스레인지 조합이 문·손잡이와 함께 정상 렌더링됨. 기존 51개 성공 장면도
  재실행해 여전히 전부 성공함을 재확인(이 수정은 "건너뛰어진 파트가 있을 때만" 동작을 바꾸므로
  다른 장면에 영향 없음).

### 3-2. 팀원의 확인

팀원은 자신의 채점 스크립트가 `write_urdfs`/`visualization_parts`를 아예 호출하지 않는 채점

## 4. Object-Level 300장 GT bbox 평가 — 사실상 전 지표 검증 완료

### 4-1. 데이터 출처

논문 Appendix B가 명시하는 "individual objects from 5 categories including 100 cabinets, 50
ovens, 50 dishwashers, 50 fridges and 50 laundry machines"에 해당하는 300장 데이터가, kitchen
평가용으로 이미 받아둔 에셋 zip(README §Evaluation 링크, `1aP6-XEzAGtmEBiDXangddSJ_IcvERlA4`)
안에 처음부터 들어있었다(`assets/{cabinets,ovens,dishwashers,fridges,washers}/`). 개수 실측:
cabinets 100 + ovens 50 + dishwashers 50 + fridges 50 + washers 50 = **300**, 논문 서술과 정확히
일치. kitchen 평가만 하느라 한 번도 열어보지 않았던 것을 팀원과의 교차검증 요청 과정에서 발견했다.

`demo.py`의 `evaluate_parts_with_masks()`/`evaluate_real_image()`를 재사용하는 신규 스크립트
`evaluate_object_metrics.py`로 300장 전체를 평가했다(300/300 성공, 실패 0건).

### 4-2. Parent Accuracy — 비교 오류였음이 밝혀짐 (2026-09-20)

- 최초 결과 0.9833을 얻고, 이를 "팀원의 Hungarian matching 버그 수정 후 값(0.9180)"과 비교해
  "논문(0.874)은 물론 팀원 값보다도 높다"고 **불일치로 잘못 보고**했었다.
- 팀원이 자신의 원본 로그(`logs/41_score_all5_gtbox_*.log` vs `logs/44_autodetect_all5_FIXED_*.log`)
  를 재확인해 알려준 바로는, **0.9180은 팀원의 GT-bbox 조건 값이 아니라 자동탐지(Finetuned
  GroundingDINO) 조건 값**이었다. 팀원의 실제 GT-bbox Parent Acc는 **0.9833**으로, 우리 값과
  분모(1354/1377)까지 완전히 일치한다.
- **원인**: 팀원이 처음 보낸 메시지에 "Parent Accuracy가 0.5394 → 0.9180으로 바뀌었다"고만 적혀
  있었고 GT-bbox/자동탐지 조건 구분이 명시돼 있지 않았는데, 우리가 이를 GT-bbox 조건일 것이라고
  임의로 가정하고 비교한 것이 오류의 원인이었다.
- **결론**: 서로 다른 사람이 독립적으로 짠 채점 코드가 소수점까지 정확히 같은 값을 낸 것으로,
  오히려 강력한 교차검증 성공 사례다. 논문(0.874)과의 차이는 우리와 팀원이 서로 다른 게 아니라
  둘 다 공통으로 겪는 별개의 미해결 항목이며, 팀원이 이미 자신의 문서에서 "원인 미확인"으로 별도
  기록해뒀다고 밝혔다.

### 4-3. Spatial Error — handle/knob 예외 처리 누락이 원인이었음, 수정 완료

- 최초 결과 0.7771을 얻고 논문(0.478)·팀원(0.4759) 대비 불일치로 보고했었다.
- 팀원이 자신의 채점 코드(`score_object_level.py` 141~147행)에 논문 Section 4가 명시하는 예외
  처리가 있음을 알려줬다: **"작은 물체(handle=mesh id 4, knob=mesh id 5)는 중심점(position_start)
  2값만 비교, 그 외 파트는 4값(시작+끝)을 비교"**. 우리 `evaluate_object_metrics.py`는 이 구분
  없이 모든 파트를 4값으로 균일하게 처리하고 있었다.
- 동일한 예외 처리를 우리 코드에도 추가해 재계산: **0.7771 → 0.4447** — 논문(0.478)·팀원(0.4759)
  과 거의 완전히 일치했다. 가설이 실측으로 확인된 사례.
- 코드 diff: `code_diff_evaluate_object_metrics_new_file.patch`. 결과 원본:
  `evaluate_object_metrics_run2.log`, `object_metrics_result.json`
  (`spatial_err_handle_knob_exception` 필드).
