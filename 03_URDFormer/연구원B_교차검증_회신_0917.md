## 1. 🔴 1순위 — Parts Spatial Error 재계산 결과

**요청**: 좌표의 0번째 padding 열을 제외하고 논문이 말한 4개 좌표 기준으로 다시 계산해서, 우리 값
1.4575가 팀원 값 1.8001과 일치하는지 확인.

**진행**:
1. `part_positions_start`/`part_positions_end`의 0번째 열을 직접 집계해 확인 — kitchen 54개 장면
   2107개 파트 **전체에서 예외 없이 값이 0으로 고정**된 padding 열임을 확인함(우연이 아님).
2. 이 열을 제외하고(`[:, 1:]` 슬라이싱을 예측·GT 양쪽에 동일하게 적용) Parts Spatial Error를
   다시 계산.

**결과**:

| 방식 | 값 |
|---|---|
| 3열 전부 사용(기존) | **1.4575** |
| 0번째 padding 열 제외(팀원 제안 방식) | **2.1863** |
| 논문 Table II (Kitchen, GT boxes, Ours) | 1.799 |
| 팀원 재현값 | 1.8001 |

**결론**: 예측과 반대로 나왔습니다. 열을 제외하니 1.4575 → **2.1863**으로, 논문(1.799)·팀원
(1.8001) 양쪽에서 오히려 더 멀어졌습니다. "패딩 열을 빼면 팀원 값과 맞아떨어질 것"이라는 가설은
실측으로 반증됐습니다.

**추정 원인(미확정)**: 논문 Section 4는 "작은 물체(handle/knob)는 중심점 2좌표만, 큰 물체(drawer/
door 등)는 4좌표(시작+끝)로 채점한다"고 명시합니다. 저희는(아마 팀원 쪽도) 이 크기별 구분 없이
모든 파트를 동일하게 처리하고 있습니다. 다만 handle/knob 파트의 `position_end`도 `position_start`
와 다른 실제 값을 갖고 있어(직접 확인), 라벨 파일 구조만으로는 "이 부분이 실제로 안 쓰인다"는 근거를
찾지 못했습니다. **이 지표는 여전히 미해결 상태입니다** — 팀원 쪽 코드에서 정확히 어떤 좌표들을
어떻게 조합해서 1.8001을 계산했는지 코드 레벨로 대조가 필요합니다.

## 2. 🔴 2순위 — Object-Level 300장 GT bbox 교차검증

**요청**: 팀원(=여러분)이 이미 300장 GT bbox + 자동탐지 정량 평가를 했다고 하니, 저희 쪽도 같은
방식으로 300장을 돌려서 서로 대조.

**먼저 확인한 사실**: 저희 쪽 기존 작업 기록을 전부 검색해봤는데, "300", "Hungarian",
"0.5394"/"0.9180" 같은 키워드가 전혀 없었습니다 — 즉 **저희는 이 300장 평가를 한 적이 없었습니다**
(10개 샘플 정성 데모만 했음). 이번에 처음 시도한 것입니다.

**발견**: kitchen 평가용으로 이미 받아둔 에셋 zip(README §Evaluation 링크,
`1aP6-XEzAGtmEBiDXangddSJ_IcvERlA4`) 안에 `assets/{cabinets,ovens,dishwashers,fridges,washers}/`
폴더가 통째로 들어있었는데, kitchen 폴더만 쓰고 이 폴더들은 한 번도 열어보지 않았습니다. 개수를
직접 세어보니:

| 카테고리 | 이미지/라벨 개수 |
|---|---|
| cabinets | 100 |
| ovens | 50 |
| dishwashers | 50 |
| fridges | 50 |
| washers | 50 |
| **합계** | **300** |

논문 Appendix B가 명시하는 "100 cabinets, 50 ovens, 50 dishwashers, 50 fridges and 50 laundry
machines"와 정확히 일치합니다.

**구현**: `evaluate.py`가 아니라 `demo.py`의 `evaluate_parts_with_masks()`/`evaluate_real_image()`를
재사용하는 새 스크립트(`evaluate_object_metrics.py`)를 작성했습니다 — 이 폴더들의 라벨 구조(물체
하나당 파일 하나, 평탄한 구조)가 kitchen의 다중 오브젝트 구조가 아니라 `demo.py`가 원래 다루는
"이미지 하나에 물체 하나" 구조와 정확히 일치하기 때문입니다. 단일 샘플로 먼저 검증(예측 mesh
`[2,4]`가 GT `[2,4]`와 정확히 일치, 예측 카테고리 `1`이 GT `1`과 정확히 일치)한 뒤 300장 전체를
실행했습니다. **300/300장 전부 성공, 실패 0건.**

**결과** (논문 Table II "Object-Level, GT Boxes, Ours" 열과 비교):

| 지표 | 논문 | 우리 재현(300장) | 비고 |
|---|---|---|---|
| Parts Mesh Acc | 0.903 | **0.9020**(1242/1377) | 거의 완전 일치 |
| Parts Parent Acc | 0.874 | 0.9833(1354/1377) | 논문보다 10%p 이상 높음 — 불일치 |
| Parts Spatial Err | 0.478 | 0.7771 | 논문보다 높음 — 불일치 |
| Base(Category) Acc | 논문 미보고 | 0.7400(222/300) | 비교 대상 없음, 참고용 |

**결론**: Mesh Acc는 거의 완벽히 일치해 우리 체크포인트·방법론 모두 신뢰할 만합니다. 하지만
**Parent Acc(0.9833)가 논문(0.874)은 물론 팀원의 버그 수정 후 값(0.9180)보다도 높습니다** — 저희와
팀원이 서로 다른 값을 얻고 있다는 뜻입니다. 팀원이 발견한 Hungarian matching/row offset 버그와
유사한 문제가 저희 계산 로직에도 남아있을 가능성, 또는 물체당 파트 수가 적어(예: cabinet 1개에
door+handle 2개) 우연히 맞힐 확률이 구조적으로 높아지는 데이터 특성 둘 다 배제하지 못했습니다.
**팀원 쪽 parent-accuracy 계산 코드(특히 Hungarian matching·row offset 수정 내역)와 직접 대조가
필요합니다.**

> `결과비교_및_원인분석.md` §2 참고.

## 3. 🟠 3순위 — Kitchen 3개 렌더링 실패, 실제로 수정 성공

**요청**: 실패한 3개 장면(28/34/48)이 왜 실패하는지 이미 알고 있다면, 실제로 고쳐서 렌더링까지
성공시킬 수 있는지 확인.

**중요한 발견 — 원래 저희 진단이 틀렸습니다**: 기존에 "파트가 1개(handle)뿐인 물체에 대해 모델이
유효 범위 밖의 parent 인덱스를 예측했다"고 진단했었는데, 이번에 실제로 고쳐보려고 디버그 프린트를
심어 전체 흐름을 추적한 결과 **이 진단이 부정확했다는 것을 발견했습니다.**

**진짜 원인**: `visualization_parts()` 함수의 두 번째 루프가 `mesh_pred==0`("none", 유효하지 않은
파트로 예측된 경우)인 파트를 **아무 링크도 만들지 않고 조용히 건너뜁니다.** 문제는 최종 URDF를
쓰는 `write_urdfs()`가 `link_names`를 "실제로 만들어진 링크만" 순서대로 압축해서 만드는데,
건너뛴 파트 이후의 파트가 가진 parent 번호(원래 번호 체계 기준)는 이 압축을 반영하지 않은 채로
남아있어서 범위를 벗어나는 것이었습니다. 실제 문제의 물체는 파트가 2개(mesh=`[0,4]`)였는데, 첫
번째 파트(mesh=0)가 건너뛰어지면서 `link_names`가 2칸(`['base_link','handle0']`)으로 압축됐고,
두 번째 파트(handle)의 parent 값 `2`(압축 전 번호 체계로는 유효했던 값)가 압축 후 목록의 범위를
벗어나 크래시가 났습니다.

**수정**: 실제로 링크가 만들어진 원본 인덱스만 순서대로 다시 번호를 매기는 매핑(`old_to_new_idx`)을
추가하고, 각 파트의 parent 참조를 이 매핑으로 변환하도록 `utils.py`를 수정했습니다(매핑에 없는 값,
즉 건너뛰어진 파트를 부모로 참조하는 경우는 base_link로 폴백). **예측값(mesh/position 등) 자체는
전혀 바꾸지 않고, 렌더링 시 링크 번호 부여 방식만 일관되게 만드는 수정입니다.**

**검증**: 수정 후 28/34/48 개별 재현 → 전부 성공. 54개 전체 재실행 → **54/54 전부 성공**(기존
51/54에서 개선). `test28.png`를 직접 열람 확인 — 캐비닛+가스레인지 조합이 문·손잡이와 함께 정상
렌더링됨. 기존 51개 성공 장면도 재실행해 여전히 전부 성공함을 재확인(이 수정은 "건너뛰어진 파트가
있을 때만" 동작을 바꾸므로 다른 장면에 영향 없음).

**결론**: kitchen 평가는 이제 **완주율 100%(54/54)**입니다. 코드 diff는
`code_diff_utils_parent_index_fix.patch`로 보존했습니다.
