# URDFormer 환경 구축 및 이슈 해결

**작성일**: 2026-09-16
**실행 환경**: i7-9700K, RAM 64GB, RTX 2080 Ti(11GB), Windows
**사용 커밋**: `ee0e77ca0e08483fd63890673c47e4a3bd68fa91`(`WEIRDLabUW/urdformer`, 김승민과 대조해 일치 확인됨)

PhysGaussian·Spring-Gaus 때와 마찬가지로 원본 저장소 README를 그대로 따라가되, 실제로 막힌 지점과
해결 방법을 기록입니다. 환경 구축(①~⑥)은 패키지 버전·설치 순서 조정만으로 해결했고, 이후 실행 단계에서
소스 코드 최소 패치 3건(⑦~⑨, §4 참고)이 추가로 필요했습니다 — 전부 최소한의 diff이며 계산 로직은
무수정입니다.

## 1. 설치 순서(README 기준)와 실제로 겪은 문제 6가지

### ① torch 설치 순서를 지켜야 함 — README 순서를 안 지켜서 겪은 문제

README는 "③ requirements.txt 먼저 → ④ torch는 별도로 나중에" 순서인데, 처음에 torch를 먼저 설치하고
requirements.txt를 나중에 돌렸더니, `requirements.txt`에 포함된 일부 패키지(`basicsr` 등)가 torch
버전을 못박지 않아 pip 의존성 해결기가 **애써 설치한 `torch==1.12.1+cu113`을 지우고 최신 torch 2.8.0으로
덮어써버렸습니다.**
- **해결**: README가 명시한 순서(requirements.txt 먼저, torch는 맨 마지막)대로 torch를 다시
  `--force-reinstall`로 재설치. 이후 `accelerate`가 "torch>=2.0.0 필요"라는 경고를 냈지만, URDFormer
  자체 코드 어디에도 `accelerate`를 직접 import하는 곳이 없어 무해함을 확인(grep으로 직접 확인).

### ② `pybullet` — Windows용 미리 빌드된 파일이 없어 소스 컴파일 필요

`pybullet==3.2.5`가 Windows+Python 3.9 조합의 사전 빌드 파일(wheel)이 PyPI에 없어, pip이 80.5MB
소스를 직접 컴파일하려다 `error: Unable to find a compatible Visual Studio installation`로 실패.
- **원인**: PhysGaussian 때 설치해둔 Visual Studio Build Tools 2022(`D:\physX_dev\tools\VSBuildTools`)가
  기본 경로가 아니라 이 세션의 PATH에 컴파일러(`cl.exe`)가 안 잡혀 있었음.
- **해결**: `vcvars64.bat`(MSVC 환경변수 설정 스크립트)를 먼저 실행한 뒤 같은 설치 명령을 재시도해서 성공.
  (참고: 일반 터미널에서 안 되면 PowerShell/cmd 조합으로 재시도하는 게 안정적이었음 — 특정 셸에서
  타임아웃 후 프로세스가 끊기는 현상이 있었음)

### ③ `grounding_dino` 설치 시 pip이 구버전 setup.py 방식을 거부

`pip install -v -e .`가 `ModuleNotFoundError: No module named 'torch'`로 실패(빌드 격리 환경에 torch가
없어서 — PhysGaussian 때도 겪은 것과 같은 종류의 문제). `--no-build-isolation`으로 우회하니 이번엔
`ERROR: ... missing the 'build_editable' hook`(최신 pip이 구버전 setup.py의 editable 설치 방식을
지원 안 함)로 다시 막힘. `--no-use-pep517` 플래그도 최신 pip(26.0.1)에서는 아예 제거되어 사용 불가.
- **해결**: `pip install` 대신 `python setup.py develop`을 직접 실행해 pip의 PEP 517 경로를 완전히 우회.

### ④ `shapely` 소스 빌드 실패(Cython/GEOS 미설치)

`python setup.py develop` 실행 중, `grounding_dino`의 하위 의존성인 `shapely`를 소스로 빌드하려다
`error: Setup script exited with ERROR: Cython is required to build shapely from source` +
`Could not find geos-config executable`로 실패.
- **해결**: `shapely`(PyPI 사전 빌드 wheel), `Cython`, `ninja`를 미리 개별 설치해서 소스 빌드 자체를
  건너뛰게 함. 같은 흐름에서 `mmdet`이 요구하는 `pycocotools`도 누락돼 있어 같이 선install.

### ⑤ NumPy 2.x ↔ 구버전 opencv-python ABI 충돌

`grounding_dino` 설치는 성공했지만, `import mmdet`이 `AttributeError: _ARRAY_API not found` /
`ImportError: numpy.core.multiarray failed to import`로 실패. 원인은 다른 패키지가 딸려 들여온
NumPy 2.0.2와, requirements.txt가 못박은 `opencv-python==4.8.0.74`(NumPy 1.x 시절 컴파일)의 ABI
불일치.
- **해결**: `pip install "numpy<2"` → 1.26.4로 다운그레이드.

### ⑥ `mmcv` 버전이 `mmdet`과 안 맞음 — README의 "예외 조건"이 사실 저희 조합에도 적용됨

`import mmdet`이 이번엔 `AssertionError: MMCV==2.2.0 is used but incompatible. Please install
mmcv>=2.0.0rc4, <2.2.0`으로 실패. README에는 "torch 2.1.0+cu12.1을 쓰는 경우에만 `mmcv<2.2.0`을
쓰라"고 조건부로 적혀 있어서 저희(torch 1.12.1+cu113)에는 해당 안 된다고 판단하고 넘어갔었는데,
**실제로는 mmdet 3.2.0 자체가 코드 레벨에서 `mmcv<2.2.0`을 강제**하고 있어 torch 버전과 무관하게
적용되는 제약이었습니다.
- **해결**: `mim install "mmcv<2.2.0"`로 재설치(2.1.0으로 낮아짐) → `import mmdet` 성공.

## 3. `get_bbox.py`의 GUI 단계 — 자동 탐지로 대체(논문 원문 근거 확인)

`get_bbox.py`는 `tkinter` 기반 대화형 GUI라 원래는 사람이 직접 박스를 확인·보정해야 합니다. 다만 논문
원문(arXiv 2405.11656)을 직접 확인한 결과:
- 논문 본문에 "interactive"·"GUI" 관련 서술이 전혀 없음
- 실제 로봇 실험 설명에는 "시스템이 장면 사진을 받아 **finetuned Grounding DINO로 자동으로** 부품을
  탐지한다"고 명시(사람 개입 언급 없음)
- 논문에 등장하는 "사람이 직접 라벨링"은 평가용 정답 데이터(54개 씬) 제작 과정이지, 파이프라인 실행
  자체가 아님
- 저자들도 자동 탐지의 한계(특히 전체 씬)를 인정하면서도 논문 실험 자체는 그대로 사용
- `get_bbox.py` 소스 코드 267~270번째 줄 주석에도 저자가 직접 "자동 GroundingDINO로 이 과정을
  자동화할 수 있다"고 적어둠

`get_bbox.py`를 그대로 쓰는 대신, 같은 파일의 자동 탐지(GroundingDINO)+저장 로직만 재사용하고 사람의
마우스 조작 없이 자동 확정하는 보조 스크립트(`auto_bbox.py`, 아래 첨부)를 작성해 실행했습니다 —
`get_bbox.py`/`labeller.py` 원본은 무수정, 새 파일만 추가.

**⚠️ 2026-09-16 정정(자기점검 결과)**: 처음엔 "자동 탐지가 GUI보다 논문 방법론에 더 가깝다"고
판단했었는데, 이건 **근거가 부족한 과장된 결론**이었음을 확인했습니다. arXiv HTML 요약(WebFetch)만
보고 판단했던 게 원인이라, 논문 원본 LaTeX 소스(`arxiv.org/e-print/2405.11656`)를 직접 받아
`experiments.tex`를 grep해서 재확인한 결과: 논문은 **"manually labeled bounding boxes"와
"GroundingDINO 자동 탐지 boxes" 둘 다를 URDFormer 입력으로 나란히 비교**합니다(Fig. 캡션 원문:
"comparing URDFormer prediction ... using (1) manually labeled bounding boxes and (2) bounding boxes
provided by fine-tuned GroundingDINO"). 즉 사람이 라벨링한 박스는 정답 데이터 생성용에 그치지 않고,
**URDF 예측의 입력 조건 중 하나로 논문에 명시적으로 쓰입니다** — GUI 도구가 논문 방법론 밖의 편의
기능이라는 주장은 틀렸습니다. 저희가 자동 탐지로 진행한 것 자체는 **논문이 실제로 테스트한 두 조건
중 하나("탐지기 기반" 조건)에는 해당**하지만, "이게 더 논문에 충실하다"는 정당화는 정정합니다 —
GUI로 직접 보정했다면 논문의 다른(더 깨끗한) 조건에 해당했을 것입니다.

## 4. 추가로 발견한 소스 코드 버그 3건(headless 실행 경로에 한정, 최소 패치)

`get_texture.py`(선택 단계) → `demo.py` 진행 중 추가로 3건을 더 발견해 최소한으로 패치했습니다
(전부 별도 첨부 파일 `수정된_소스파일들/`에 있음, diff는 파일 상단 주석에 그대로 남겨둠).

### ⑦ `texture.py` — "선택사항"인데 실제로는 강제 실행되던 문제

README는 `get_texture.py`를 "선택사항, 건너뛰어도 URDF만 얻을 수 있다"고 명시하지만, `texture.py`가
Stability AI의 **gated 모델**(`stable-diffusion-2-depth`, `stable-diffusion-2-inpainting` — HuggingFace
로그인+라이선스 동의 필요)을 **모듈을 import하는 순간 무조건** 다운로드하려 시도해서, `--texture` 없이
`demo.py`를 실행해도 똑같이 실패했습니다. 라이선스 동의는 저희가 대신 처리할 수 없는 부분이라(계정·약관
동의가 필요), 코드가 README에 적힌 대로 "실제로 쓸 때만" 로드하도록 지연 로딩으로 수정 — 계산 로직은
무수정, 로딩 시점만 변경.

### ⑧ `demo.py` — `--headless` 모드의 렌더러가 실제로는 안 되는 조합이었음

`--headless`(즉 `p.DIRECT` 연결, 창 없음) 모드에서만 호출되는 `traj_camera()` 함수가 실제 창의
OpenGL 컨텍스트가 필요한 `renderer=p.ER_BULLET_HARDWARE_OPENGL`을 그대로 써서 `IndexError`로 실패.
DIRECT 연결에 맞는 CPU 소프트웨어 렌더러(`ER_TINY_RENDERER`)로 교체.

### ⑨ `demo.py` — pybullet 컬러 이미지 반환 형식이 이 빌드에서는 다름

Windows용 사전 빌드 파일이 없어 pybullet을 소스에서 직접 컴파일했는데(②), 이 빌드는 `getCameraImage`가
색상값을 `(512,512,4)` 배열이 아니라 **평탄화된 1차원 int32 튜플**로 반환한다는 걸 직접 테스트로
확인했습니다. `reshape((512,512,4))` + `uint8` 캐스팅을 추가해 해결(PIL이 int32는 저장 못 함).

## 5. 최종 재현 결과 — 성공

README 기본 예제(`images/` 폴더의 캐비닛류 사진 10장, `--scene_type object`)로 전체 파이프라인
(자동 박스 탐지 → URDF 예측 → pybullet 물리 시뮬레이션 → 20프레임 애니메이션 렌더링)이 끝까지
정상 작동함을 확인했습니다.

- 10개 이미지 전부 `.urdf` 파일 생성 완료(`결과URDF/` 폴더에 2개 예시 첨부)
- 이미지당 20프레임씩 총 200장 렌더링 완료(`샘플이미지/`에 대표 2쌍 — 입력사진+생성된 3D 애니메이션 프레임 — 첨부)
- 생성된 URDF를 직접 열어보면 서랍(prismatic joint), 문(revolute joint, 회전축·각도 제한값까지 포함),
  손잡이·노브(fixed joint)가 실제 캐비닛 구조에 맞게 부모-자식 관계로 정확히 생성됨을 확인(예시:
  `label13.urdf` — 서랍 2개+문 2개+손잡이 2개+노브 2개, 전부 올바른 관절 타입)
- 렌더링된 애니메이션 이미지를 직접 열어봐서 육안으로도 확인 — 서랍이 열리고 문이 회전해서 열리는
  모습이 실제로 자연스럽게 나옴

## 6. 노트북 힌지·로봇팔 시도 — 결과: 논문 범주 밖이라 의미 있는 결과 안 나옴 (솔직 보고)

캐비닛류 재현이 성공한 뒤, 원래 목적(교수님이 예시로 든 노트북 힌지·로봇팔)에 같은 파이프라인을
그대로 적용해봤습니다. 입력 이미지는 저희가 촬영한 게 아니라 **Wikimedia Commons의 퍼블릭
도메인/CC 라이선스 사진**을 사용했습니다(노트북: Jon Sullivan 작, 퍼블릭 도메인 / 로봇팔: Universal
Robots UR16e, CC BY-SA 4.0 — 출처는 첨부 이미지 폴더 참고).

**결과: 예상대로 의미 없는 출력이 나왔습니다.**
- **노트북** → 화면을 "캐비닛 문"으로, 트랙패드를 "둥근 손잡이"로 잘못 인식해 엉뚱한 캐비닛 모양의
  URDF가 생성됨. 힌지(화면-키보드 사이 회전축) 개념 자체가 반영되지 않음.
- **로봇팔** → 관절 구조를 전혀 인식하지 못하고, 5개 학습 카테고리 중 하나(세탁기 형태로 추정)로
  억지로 끼워 맞춰진 결과가 나옴. 실제 로봇팔의 다관절 구조와는 무관한 형태.

**원인**: §2에서 이미 확인했듯 GroundingDINO의 유효 박스 라벨이 `drawer, door, handle, knob` 등
캐비닛 부품명으로 고정되어 있고, URDFormer 본체도 5개 카테고리(cabinet/oven/dishwasher/fridge/washer)
로만 학습되어 있습니다. 노트북·로봇팔은 이 어휘·카테고리 어디에도 해당하지 않아, "탐지 정확도가
낮다"는 수준이 아니라 **애초에 표현할 방법이 없는 대상**이었습니다. 이는 착수 전 예상(§2)과 정확히
일치하는 결과입니다.

입력/결과 이미지는 `샘플이미지_한계테스트/`, 생성된 URDF는 `결과URDF/laptop.urdf`,
`결과URDF/robotarm.urdf`에 첨부했습니다(결과 자체가 무의미하다는 걸 보여주기 위한 증빙 목적).

## 7. "완벽 재현" 검증 — 논문의 정량 지표는 공개 코드로 재현 불가능함을 확인

**"논문이 주장한 정확도 수치까지 맞춰봤는가"**를 검증하려고 `evaluate.py`(54개 주방 씬, 정답
바운딩박스 사용)를 분석했습니다. 결론: **이 스크립트로는 애초에 논문의 정량 수치를 재현할 수 없습니다.**

- 논문 본문(arXiv 2405.11656)에는 실제로 정량 지표가 있습니다 — Table II(Ablation): Mesh Accuracy
  0.407~0.740, Parent Accuracy 0.8~0.87, Spatial Error 0.478~3.107, Recall/Precision. Table I(로봇
  실험): 전체 작업 성공률 78%, 문 열고 닫기 85%. 평가 방법(§IV-B4)도 IoU 기반 박스 정합 + Hungarian
  matching으로 명시되어 있음.
- 하지만 공개된 `evaluate.py` 소스를 직접 읽어보니, 정답값(`position_gt`, `mesh_gt`, `parent_gt` 등)을
  **딱 한 줄(329번째 줄)에서 불러오기만 하고 이후 코드 전체에서 단 한 번도 다시 참조되지 않습니다**
  (`grep`으로 전체 파일 확인) — 즉 예측값과 정답값을 비교해 점수를 매기는 로직 자체가 빠져 있습니다.
- 대신 이 스크립트는 `p.connect(p.GUI)`(실제 창 필요)와 매 씬마다 `breakpoint()`(사람이 직접 다음으로
  넘겨야 하는 Python 디버거 정지)로 구성되어 있어, **사람이 앉아서 54개 씬을 하나씩 눈으로 비교하는
  용도로만 설계**되어 있습니다.
- 공식 프로젝트 웹사이트(urdformer.github.io)도 재확인했는데, URDF 예측 정확도 수치는 어디에도
  없고(탐지 모델의 F1 스코어 언급만 있음 — 이는 별개 지표) 정성적 시각화·영상만 제공합니다.

**정리**: "논문에 정량 지표가 없다"가 아니라 **"논문에는 있지만 그걸 계산하는 코드가 공개 저장소에는
빠져 있다"**가 정확한 표현입니다. 이는 저희가 더 시도한다고 해결되는 문제가 아니라 공개 코드 자체의
구조적 한계이며, 따라서 **논문의 정량적 수치까지 완전히 일치시키는 "완벽한" 재현은 이 릴리즈만으로는
원천적으로 불가능**합니다. 저희가 확인할 수 있는 최선은 §5의 정성적 확인(생성된 URDF 구조가 실제
캐비닛 형태와 논리적으로 맞는지 직접 검사)까지입니다.

## 8. 결론

환경 구축 이슈 6건(①~⑥, 패키지 버전) + 추가 소스 버그 3건(⑦~⑨, headless 실행 경로 한정 최소 패치)을
해결하고, **URDFormer 파이프라인(GroundingDINO 자동 탐지 조건)을 논문의 캐비닛류 카테고리에서 끝까지
성공적으로 재현**했습니다(정성적 검증 기준). §3에서 자동 탐지로 진행한 근거를 "논문 방법론에 더
가깝다"고 정당화했었으나, 이는 §3 말미에서 정정한 대로 **과장된 결론이었고 원본 LaTeX 소스 확인 후
철회**합니다 — 정확히는 "논문이 실제로 테스트한 두 조건(수동 라벨링 vs 자동 탐지) 중 하나를 재현한
것"이며, 어느 쪽이 "더 논문에 충실한가"라는 우열은 없습니다. 논문의 정량 지표(Table I·II)는 공개
코드에 계산 로직이 없어 재현이 원천적으로 불가능함을 확인했습니다(§7). 노트북 힌지·로봇팔은 **논문의
학습 범주를 완전히 벗어나 있어 이 논문으로는 재현할 수 없음을 실제로 확인**했습니다(§6) — 이 부분은
애초에 저희가 메일에서 말씀드렸던 대로 **PhysX-3D 쪽에서 다뤄야 하는 영역**이라는 판단이 실측으로도
뒷받침됐습니다. 다음 단계는 PhysX-3D(5090/Linux)로 이어갑니다.
