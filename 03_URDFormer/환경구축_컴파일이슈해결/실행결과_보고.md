# URDFormer 환경 구축 및 이슈 해결

**작성일**: 2026-09-16
**실행 환경**: i7-9700K, RAM 64GB, RTX 2080 Ti(11GB), Windows
**사용 커밋**: `ee0e77ca0e08483fd63890673c47e4a3bd68fa91`(`WEIRDLabUW/urdformer`, 김승민과 대조해 일치 확인됨)

PhysGaussian·Spring-Gaus 때와 마찬가지로 원본 저장소 README를 그대로 따라가되, 실제로 막힌 지점과
해결 방법을 기록입니다. 환경 구축(①~⑥)은 패키지 버전·설치 순서 조정만으로 해결했고, 이후 실행 단계에서
소스 코드 최소 패치 3건(⑦~⑨, §4 참고)이 추가로 필요했습니다 — 전부 최소한의 diff이며 계산 로직은
무수정입니다.

## 1. 설치 순서(README 기준)와 실제로 겪은 문제 6가지

### ① torch 설치 순서를 지켜야 함 — README 순서를 안 지켜서 겪은 문제

README는 "③ requirements.txt 먼저 → ④ torch는 별도로 나중에" 순서인데, 처음에 torch를 먼저 설치하고
requirements.txt를 나중에 돌렸더니, `requirements.txt`에 포함된 일부 패키지(`basicsr` 등)가 torch
버전을 못박지 않아 pip 의존성 해결기가 **애써 설치한 `torch==1.12.1+cu113`을 지우고 최신 torch 2.8.0으로
덮어써버렸습니다.**
- **해결**: README가 명시한 순서(requirements.txt 먼저, torch는 맨 마지막)대로 torch를 다시
  `--force-reinstall`로 재설치. 이후 `accelerate`가 "torch>=2.0.0 필요"라는 경고를 냈지만, URDFormer
  자체 코드 어디에도 `accelerate`를 직접 import하는 곳이 없어 무해함을 확인(grep으로 직접 확인).

### ② `pybullet` — Windows용 미리 빌드된 파일이 없어 소스 컴파일 필요

`pybullet==3.2.5`가 Windows+Python 3.9 조합의 사전 빌드 파일(wheel)이 PyPI에 없어, pip이 80.5MB
소스를 직접 컴파일하려다 `error: Unable to find a compatible Visual Studio installation`로 실패.
- **원인**: PhysGaussian 때 설치해둔 Visual Studio Build Tools 2022(`D:\physX_dev\tools\VSBuildTools`)가
  기본 경로가 아니라 이 세션의 PATH에 컴파일러(`cl.exe`)가 안 잡혀 있었음.
- **해결**: `vcvars64.bat`(MSVC 환경변수 설정 스크립트)를 먼저 실행한 뒤 같은 설치 명령을 재시도해서 성공.
  (참고: 일반 터미널에서 안 되면 PowerShell/cmd 조합으로 재시도하는 게 안정적이었음 — 특정 셸에서
  타임아웃 후 프로세스가 끊기는 현상이 있었음)

### ③ `grounding_dino` 설치 시 pip이 구버전 setup.py 방식을 거부

`pip install -v -e .`가 `ModuleNotFoundError: No module named 'torch'`로 실패(빌드 격리 환경에 torch가
없어서 — PhysGaussian 때도 겪은 것과 같은 종류의 문제). `--no-build-isolation`으로 우회하니 이번엔
`ERROR: ... missing the 'build_editable' hook`(최신 pip이 구버전 setup.py의 editable 설치 방식을
지원 안 함)로 다시 막힘. `--no-use-pep517` 플래그도 최신 pip(26.0.1)에서는 아예 제거되어 사용 불가.
- **해결**: `pip install` 대신 `python setup.py develop`을 직접 실행해 pip의 PEP 517 경로를 완전히 우회.

### ④ `shapely` 소스 빌드 실패(Cython/GEOS 미설치)

`python setup.py develop` 실행 중, `grounding_dino`의 하위 의존성인 `shapely`를 소스로 빌드하려다
`error: Setup script exited with ERROR: Cython is required to build shapely from source` +
`Could not find geos-config executable`로 실패.
- **해결**: `shapely`(PyPI 사전 빌드 wheel), `Cython`, `ninja`를 미리 개별 설치해서 소스 빌드 자체를
  건너뛰게 함. 같은 흐름에서 `mmdet`이 요구하는 `pycocotools`도 누락돼 있어 같이 선install.

### ⑤ NumPy 2.x ↔ 구버전 opencv-python ABI 충돌

`grounding_dino` 설치는 성공했지만, `import mmdet`이 `AttributeError: _ARRAY_API not found` /
`ImportError: numpy.core.multiarray failed to import`로 실패. 원인은 다른 패키지가 딸려 들여온
NumPy 2.0.2와, requirements.txt가 못박은 `opencv-python==4.8.0.74`(NumPy 1.x 시절 컴파일)의 ABI
불일치.
- **해결**: `pip install "numpy<2"` → 1.26.4로 다운그레이드.

### ⑥ `mmcv` 버전이 `mmdet`과 안 맞음 — README의 "예외 조건"이 사실 저희 조합에도 적용됨

`import mmdet`이 이번엔 `AssertionError: MMCV==2.2.0 is used but incompatible. Please install
mmcv>=2.0.0rc4, <2.2.0`으로 실패. README에는 "torch 2.1.0+cu12.1을 쓰는 경우에만 `mmcv<2.2.0`을
쓰라"고 조건부로 적혀 있어서 저희(torch 1.12.1+cu113)에는 해당 안 된다고 판단하고 넘어갔었는데,
**실제로는 mmdet 3.2.0 자체가 코드 레벨에서 `mmcv<2.2.0`을 강제**하고 있어 torch 버전과 무관하게
적용되는 제약이었습니다.
- **해결**: `mim install "mmcv<2.2.0"`로 재설치(2.1.0으로 낮아짐) → `import mmdet` 성공.

## 3. `get_bbox.py`의 GUI 단계 — 자동 탐지로 대체(논문 원문 근거 확인)

`get_bbox.py`는 `tkinter` 기반 대화형 GUI라 원래는 사람이 직접 박스를 확인·보정해야 합니다. 다만 논문
원문(arXiv 2405.11656)을 직접 확인한 결과:
- 논문 본문에 "interactive"·"GUI" 관련 서술이 전혀 없음
- 실제 로봇 실험 설명에는 "시스템이 장면 사진을 받아 **finetuned Grounding DINO로 자동으로** 부품을
  탐지한다"고 명시(사람 개입 언급 없음)
- 논문에 등장하는 "사람이 직접 라벨링"은 평가용 정답 데이터(54개 씬) 제작 과정이지, 파이프라인 실행
  자체가 아님
- 저자들도 자동 탐지의 한계(특히 전체 씬)를 인정하면서도 논문 실험 자체는 그대로 사용
- `get_bbox.py` 소스 코드 267~270번째 줄 주석에도 저자가 직접 "자동 GroundingDINO로 이 과정을
  자동화할 수 있다"고 적어둠

`get_bbox.py`를 그대로 쓰는 대신, 같은 파일의 자동 탐지(GroundingDINO)+저장 로직만 재사용하고 사람의
마우스 조작 없이 자동 확정하는 보조 스크립트(`auto_bbox.py`, 아래 첨부)를 작성해 실행했습니다 —
`get_bbox.py`/`labeller.py` 원본은 무수정, 새 파일만 추가.

**⚠️ 2026-09-16 정정(자기점검 결과)**: 처음엔 "자동 탐지가 GUI보다 논문 방법론에 더 가깝다"고
판단했었는데, 이건 **근거가 부족한 과장된 결론**이었음을 확인했습니다. arXiv HTML 요약(WebFetch)만
보고 판단했던 게 원인이라, 논문 원본 LaTeX 소스(`arxiv.org/e-print/2405.11656`)를 직접 받아
`experiments.tex`를 grep해서 재확인한 결과: 논문은 **"manually labeled bounding boxes"와
"GroundingDINO 자동 탐지 boxes" 둘 다를 URDFormer 입력으로 나란히 비교**합니다(Fig. 캡션 원문:
"comparing URDFormer prediction ... using (1) manually labeled bounding boxes and (2) bounding boxes
provided by fine-tuned GroundingDINO"). 즉 사람이 라벨링한 박스는 정답 데이터 생성용에 그치지 않고,
**URDF 예측의 입력 조건 중 하나로 논문에 명시적으로 쓰입니다** — GUI 도구가 논문 방법론 밖의 편의
기능이라는 주장은 틀렸습니다. 저희가 자동 탐지로 진행한 것 자체는 **논문이 실제로 테스트한 두 조건
중 하나("탐지기 기반" 조건)에는 해당**하지만, "이게 더 논문에 충실하다"는 정당화는 정정합니다 —
GUI로 직접 보정했다면 논문의 다른(더 깨끗한) 조건에 해당했을 것입니다.

## 4. 추가로 발견한 소스 코드 버그 3건(headless 실행 경로에 한정, 최소 패치)

`get_texture.py`(선택 단계) → `demo.py` 진행 중 추가로 3건을 더 발견해 최소한으로 패치했습니다
(전부 별도 첨부 파일 `수정된_소스파일들/`에 있음, diff는 파일 상단 주석에 그대로 남겨둠).

### ⑦ `texture.py` — "선택사항"인데 실제로는 강제 실행되던 문제

README는 `get_texture.py`를 "선택사항, 건너뛰어도 URDF만 얻을 수 있다"고 명시하지만, `texture.py`가
Stability AI의 **gated 모델**(`stable-diffusion-2-depth`, `stable-diffusion-2-inpainting` — HuggingFace
로그인+라이선스 동의 필요)을 **모듈을 import하는 순간 무조건** 다운로드하려 시도해서, `--texture` 없이
`demo.py`를 실행해도 똑같이 실패했습니다. 라이선스 동의는 저희가 대신 처리할 수 없는 부분이라(계정·약관
동의가 필요), 코드가 README에 적힌 대로 "실제로 쓸 때만" 로드하도록 지연 로딩으로 수정 — 계산 로직은
무수정, 로딩 시점만 변경.

**⚠️ 2026-09-16 추가 확인 — `--texture`는 현재 시점에 실질적으로 사용 불가능함**: 사용자가 실제
HuggingFace 계정으로 로그인한 상태에서도 두 모델 페이지 접근이 거부됨을 직접 확인. HuggingFace API로
비로그인 조회(`GET /api/models/stabilityai/stable-diffusion-2-depth`, `.../stable-diffusion-2-inpainting`
둘 다)해도 401 응답. 웹 검색으로 원인 확인: Stability AI가 2026년 EU AI Act 규제 대응 목적으로
**Stable Diffusion 2.0/2.1 계열 모델(이 두 모델 포함)을 공식적으로 정리(deprecate)**했음 — URDFormer가
2024년 릴리즈될 당시엔 공개 접근 가능했던 외부 의존성이, 저희 재현 시점(2026)에는 모델 소유자 측
정책 변경으로 사라진 것. **저희 쪽 설정·코드 문제가 아니라 외부 의존성 자체의 가용성 문제이며, 현재
시점에 공식 경로로는 텍스처 생성 기능을 재현할 방법이 없음.** URDF 구조 예측(§8 정량 검증의 대상)에는
영향 없음 — 텍스처는 시각적 표현에만 관여.

### ⑧ `demo.py` — `--headless` 모드의 렌더러가 실제로는 안 되는 조합이었음

`--headless`(즉 `p.DIRECT` 연결, 창 없음) 모드에서만 호출되는 `traj_camera()` 함수가 실제 창의
OpenGL 컨텍스트가 필요한 `renderer=p.ER_BULLET_HARDWARE_OPENGL`을 그대로 써서 `IndexError`로 실패.
DIRECT 연결에 맞는 CPU 소프트웨어 렌더러(`ER_TINY_RENDERER`)로 교체.

### ⑨ `demo.py` — pybullet 컬러 이미지 반환 형식이 이 빌드에서는 다름

Windows용 사전 빌드 파일이 없어 pybullet을 소스에서 직접 컴파일했는데(②), 이 빌드는 `getCameraImage`가
색상값을 `(512,512,4)` 배열이 아니라 **평탄화된 1차원 int32 튜플**로 반환한다는 걸 직접 테스트로
확인했습니다. `reshape((512,512,4))` + `uint8` 캐스팅을 추가해 해결(PIL이 int32는 저장 못 함).

## 5. 최종 재현 결과 — 성공

README 기본 예제(`images/` 폴더의 캐비닛류 사진 10장, `--scene_type object`)로 전체 파이프라인
(자동 박스 탐지 → URDF 예측 → pybullet 물리 시뮬레이션 → 20프레임 애니메이션 렌더링)이 끝까지
정상 작동함을 확인했습니다.

- 10개 이미지 전부 `.urdf` 파일 생성 완료(`결과URDF/` 폴더에 2개 예시 첨부)
- 이미지당 20프레임씩 총 200장 렌더링 완료(`샘플이미지/`에 대표 2쌍 — 입력사진+생성된 3D 애니메이션 프레임 — 첨부)
- 생성된 URDF를 직접 열어보면 서랍(prismatic joint), 문(revolute joint, 회전축·각도 제한값까지 포함),
  손잡이·노브(fixed joint)가 실제 캐비닛 구조에 맞게 부모-자식 관계로 정확히 생성됨을 확인(예시:
  `label13.urdf` — 서랍 2개+문 2개+손잡이 2개+노브 2개, 전부 올바른 관절 타입)
- 렌더링된 애니메이션 이미지를 직접 열어봐서 육안으로도 확인 — 서랍이 열리고 문이 회전해서 열리는
  모습이 실제로 자연스럽게 나옴

## 6. 노트북 힌지·로봇팔 시도 — 결과: 논문 범주 밖이라 의미 있는 결과 안 나옴 (솔직 보고)

캐비닛류 재현이 성공한 뒤, 원래 목적(교수님이 예시로 든 노트북 힌지·로봇팔)에 같은 파이프라인을
그대로 적용해봤습니다. 입력 이미지는 저희가 촬영한 게 아니라 **Wikimedia Commons의 퍼블릭
도메인/CC 라이선스 사진**을 사용했습니다(노트북: Jon Sullivan 작, 퍼블릭 도메인 / 로봇팔: Universal
Robots UR16e, CC BY-SA 4.0 — 출처는 첨부 이미지 폴더 참고).

**결과: 예상대로 의미 없는 출력이 나왔습니다.**
- **노트북** → 화면을 "캐비닛 문"으로, 트랙패드를 "둥근 손잡이"로 잘못 인식해 엉뚱한 캐비닛 모양의
  URDF가 생성됨. 힌지(화면-키보드 사이 회전축) 개념 자체가 반영되지 않음.
- **로봇팔** → 관절 구조를 전혀 인식하지 못하고, 5개 학습 카테고리 중 하나(세탁기 형태로 추정)로
  억지로 끼워 맞춰진 결과가 나옴. 실제 로봇팔의 다관절 구조와는 무관한 형태.

**원인**: §2에서 이미 확인했듯 GroundingDINO의 유효 박스 라벨이 `drawer, door, handle, knob` 등
캐비닛 부품명으로 고정되어 있고, URDFormer 본체도 5개 카테고리(cabinet/oven/dishwasher/fridge/washer)
로만 학습되어 있습니다. 노트북·로봇팔은 이 어휘·카테고리 어디에도 해당하지 않아, "탐지 정확도가
낮다"는 수준이 아니라 **애초에 표현할 방법이 없는 대상**이었습니다. 이는 착수 전 예상(§2)과 정확히
일치하는 결과입니다.

입력/결과 이미지는 `샘플이미지_한계테스트/`, 생성된 URDF는 `결과URDF/laptop.urdf`,
`결과URDF/robotarm.urdf`에 첨부했습니다(결과 자체가 무의미하다는 걸 보여주기 위한 증빙 목적).

## 7. "완벽 재현" 검증 — 논문의 정량 지표는 공개 코드로 재현 불가능함을 확인

**"논문이 주장한 정확도 수치까지 맞춰봤는가"**를 검증하려고 `evaluate.py`(54개 주방 씬, 정답
바운딩박스 사용)를 분석했습니다. 결론: **이 스크립트로는 애초에 논문의 정량 수치를 재현할 수 없습니다.**

- 논문 본문(arXiv 2405.11656)에는 실제로 정량 지표가 있습니다 — Table II(Ablation): Mesh Accuracy
  0.407~0.740, Parent Accuracy 0.8~0.87, Spatial Error 0.478~3.107, Recall/Precision. Table I(로봇
  실험): 전체 작업 성공률 78%, 문 열고 닫기 85%. 평가 방법(§IV-B4)도 IoU 기반 박스 정합 + Hungarian
  matching으로 명시되어 있음.
- 하지만 공개된 `evaluate.py` 소스를 직접 읽어보니, 정답값(`position_gt`, `mesh_gt`, `parent_gt` 등)을
  **딱 한 줄(329번째 줄)에서 불러오기만 하고 이후 코드 전체에서 단 한 번도 다시 참조되지 않습니다**
  (`grep`으로 전체 파일 확인) — 즉 예측값과 정답값을 비교해 점수를 매기는 로직 자체가 빠져 있습니다.
- 대신 이 스크립트는 `p.connect(p.GUI)`(실제 창 필요)와 매 씬마다 `breakpoint()`(사람이 직접 다음으로
  넘겨야 하는 Python 디버거 정지)로 구성되어 있어, **사람이 앉아서 54개 씬을 하나씩 눈으로 비교하는
  용도로만 설계**되어 있습니다.
- 공식 프로젝트 웹사이트(urdformer.github.io)도 재확인했는데, URDF 예측 정확도 수치는 어디에도
  없고(탐지 모델의 F1 스코어 언급만 있음 — 이는 별개 지표) 정성적 시각화·영상만 제공합니다.

**정리(2026-09-16 갱신 — §8에서 뒤집힘)**: "논문에 정량 지표가 없다"가 아니라 **"논문에는 있지만 그걸
계산하는 코드가 공개 저장소에는 빠져 있다"**가 정확한 표현입니다. **처음엔 이를 "원천적으로 불가능"이라고
판단했으나, 이는 성급한 결론이었습니다** — 정답값과 예측값이 이미 다 계산되어 있고 논문이 계산 방법을
상세히 설명해뒀기 때문에, 저희가 채점 로직만 직접 구현하면 됩니다. 실제로 구현해서 돌린 결과는 §8에
있습니다.

일치**함을 직접 세어서 확인했습니다. 또한 `evaluate.py`의 텍스처 로직은 실제 실행 경로에서는 gated

import가 안 돼 있어 실행하면 에러가 나는 죽은 코드였음).

**채점 스크립트 직접 구현**(`score_object_level.py`, 신규 작성, URDFormer 원본 코드는 무수정 — `demo.py`/
`evaluate.py`에 이미 있는 예측 함수만 그대로 재사용): 논문 §Evaluation Metrics에 설명된 category
accuracy·parent accuracy·spatial error를 계산하는 로직을 새로 작성. Object-Level `cabinets` 100개
이미지(진짜 정답 박스를 입력으로 사용, 논문의 "GT boxes" 조건과 동일) 전체에 대해 실행.

**논문 원본 LaTeX 테이블(`tables/baseline_gen_texture.tex`, arXiv e-print 소스에서 직접 확인 — 이전에
WebFetch 요약으로 인용했던 "0.407~0.740" 범위는 부정확했으며, 실제로는 Kitchen/Object-Level ×
GT박스/자동탐지 × Global/Parts로 세분화된 표였음)에서, 저희 조건(Object-Level·GT박스·Parts·"Ours" 열)에
정확히 해당하는 셀과 대조:

| 지표 | 논문 원본(Object-Level, GT박스, Parts, "Ours") | 저희 실측(1차, 버그 있음) | 저희 실측(수정 후) | 비교 |
|---|---|---|---|---|
| Mesh(category) Accuracy | **0.903** | 0.8938 | 0.8938 | 거의 일치(오차 1%p) |
| Parent Accuracy | **0.874** | 0.5018 | **0.9916** | 근접(오차 12%p, 저희가 더 높음) |
| Spatial Error | **0.478** | 0.9219 | **0.4355** | 거의 일치(오차 0.04) |

**1차 결과에서 발견한 버그 2건과 수정**:
1. **Parent Accuracy 버그**: 정답 관계 행렬(`part_relations`)에서 파트 i의 실제 관계는
   `row[num_roots+i]`에 있는데(0번 행은 루트 자신 몫이라 전부 0 — `argmax` 직접 찍어서 확인), 예측값
   쪽(`parent_pred[num_roots+i]`)은 이 오프셋을 맞게 썼으면서 정답값 쪽만 `part_relations_gt[i]`로
   오프셋을 빠뜨렸음. 수정 후 0.5018 → **0.9916**로 급등(논문 0.874와 근접한 범위로 정상화).
2. **Spatial Error 버그**: 논문 §Evaluation Metrics 원문 — "손잡이·노브 같은 작은 부품은 중심점(x1,y1)
   2개 값만 비교한다"고 명시되어 있는데, 처음엔 모든 부품에 대해 시작+끝 4개 값을 동일하게 비교해서
   손잡이/노브에 불필요한 오차가 더해지고 있었음. `mesh_gt`가 handle(4)·knob(5)인 경우만 중심점만
   비교하도록 수정 후 0.9219 → **0.4355**로 감소(논문 0.478과 사실상 일치).

**Mesh Accuracy가 처음부터 논문과 거의 정확히 일치**했던 것은 체크포인트 로딩·데이터 파싱·모델 추론까지
파이프라인 전체가 정확하다는 강한 증거였고, 실제로 나머지 두 지표의 원인은 모델이나 재현의 문제가
아니라 **저희가 새로 작성한 채점 스크립트의 인덱싱·조건 분기 버그 2건**이었음이 확인됐습니다. 수정
후에는 **3개 지표 모두 논문 원본과 근접하게 일치**합니다(cabinets 단일 카테고리 vs 논문은 5개 카테고리
평균이라는 차이가 있어 완전히 같은 숫자가 나올 이유는 없으며, 이 정도 근접도면 재현 성공으로 판단할
근거가 충분합니다).

**채점 대상 100장 중 3장(test0/test5/test20)을 실제로 렌더링해서 육안 확인**(`demo.py` 무수정 재사용,
정답 박스를 `grounding_dino/labels_manual/`에 넣어 그대로 실행) — 입력 사진과 생성된 구조를
`정량평가_렌더링결과/`에 첨부했습니다. 3장 모두 문/서랍/손잡이/노브 개수와 배치가 원본 사진과
정확히 일치하는 것을 직접 확인했습니다(예: test5 — 서랍 2개+문 2개+노브 4개, test20 — 서랍 1개(노브)+
문 2개(손잡이) 구조까지 정확히 재현).

### 9-3. Parent Accuracy 정밀 재검증 — 실제 버그 발견·수정 (2026-09-16, 사용자 지시로 정밀 감사)

처음엔 "원인 미상"으로 남겼으나, 사용자가 "평가 구현 자체가 논문 정의와 일치하는지부터 검증하라"고
지시해 샘플 단위로 직접 추적한 결과 **자동탐지 조건에서 실제 구현 버그를 발견·확정·수정**했습니다.
상세 A~J 형식 전체 분석은 별도 문서(`physX/0916/Parent_Accuracy_정밀분석.md`)에 원문 그대로 있고,
핵심만 요약하면:

- **버그**: 자동탐지 조건은 예측 박스 순서가 정답 박스 순서와 다른데(GroundingDINO 탐지 순서는 라벨링
  순서와 무관), "예측 박스의 parent가 가리키는 인덱스"와 "정답 박스의 parent가 가리키는 인덱스"를
  서로 다른 두 좌표계인 채로 직접 비교하고 있었습니다.
- **샘플 단위 증거**(`cabinets/test0.jpg`): 예측박스0(손잡이)의 parent가 "예측박스2"를 가리키는데,
  예측박스2는 Hungarian matching으로 정답박스0(문)에 매칭되어 있고, 정답박스1(손잡이)의 실제 parent도
  정답박스0 — **번역하면 정확히 맞는 예측인데, 인덱스를 그대로 비교해서 틀렸다고 오채점**하고 있었음을
  직접 확인.
- **수정**: 예측 parent가 가리키는 예측-파트를, 그 예측-파트가 매칭된 정답-파트 번호로 번역한 뒤 비교하도록
  수정. root(물체 본체) 인덱스는 두 좌표계에서 공유되는 값이라 그대로 비교.
- **결과**: 자동탐지 조건 Parent Accuracy **0.5394 → 0.9180**으로 급등, 논문(0.826)과의 오차가
  −28.7%p(더 낮음)에서 **+9.2%p(더 높음)로 좁혀짐**.

**남은 불일치(정직하게 유지)**: 수정 후에도 **GT박스 조건(+10.9%p)과 자동탐지 조건(+9.2%p) 둘 다
논문보다 비슷한 폭으로 높습니다** — 방향과 크기가 비슷해진 것 자체가 "공통된 원인 하나가 남아있을
가능성"을 시사하지만, 그 원인은 root/non-root 분리 재검증(300장 전체: root-parent 713/713=100%,
non-root-parent 641/664=96.5%, 둘 다 개별적으로도 매우 높아 "대부분 root라 쉽다"는 가설은 기각)까지
포함해 추가로 점검했으나 **확정하지 못했습니다**. 검증 안 된 가설(체크포인트/평가데이터 버전 차이,
집계 방식 해석 차이, FP/FN의 분모 포함 여부 등)만 `Parent_Accuracy_정밀분석.md` §G에 나열했고, 논문
수치에 맞추기 위해 이 가설들을 근거 없이 적용하지는 않았습니다.

### 9-5. Kitchen 54씬 GT박스 조건 — 전체 실행 완료 (2026-09-17)

8개 지표 중 7개가 논문과 오차 0.1%p 이내로 사실상 일치합니다. n=486 objects(Global), 2107 parts(Parts).

**구현 과정에서 발견한 중요 사항 — "Global Mesh Accuracy" 필드 재확인(임의 조정 아님, 근거 기반 수정)**:
처음에는 `data['meshes']`(global-level 필드)를 `mesh_pred_global`(global 모델 예측)과 직접 비교했더니
Mesh Acc=1.0000(무의미)이 나왔습니다. 직접 전수 조사한 결과 **`data['meshes']`는 54개 scene, 486개
object 전체에서 값이 예외 없이 0으로 고정**되어 있어 비교 자체가 상수 예측 문제였고, 게다가
`evaluate.py`의 `evaluate()` 함수 자체도 `mesh_pred_global`의 "값"을 한 번도 사용하지 않습니다
(`for mesh_id, each_mesh in enumerate(mesh_pred_global)` — `each_mesh` 변수가 loop body에서 재참조
안 됨, grep으로 직접 확인). 대신 각 오브젝트의 실제 카테고리(cabinet/shelf/oven/dishwasher/washer/
fridge)는 오브젝트 크롭을 **Part 모델**에 통과시켜 얻는 `base_pred` 출력이고(`evaluate()`의
`base_types.append(base_pred[0])`), 이에 대응하는 정답 필드는 `data['part_bases']`(이름은 "part_"이지만
실제로는 scene당 10개 object 각각의 카테고리를 담은 배열 — 값 분포 1=cabinet 393, 2=shelf 30,
6=other 24, 3=oven 20, 5=washer 18, 7=fridge 1로 실제 분산 있음, `process_prediction()`이 쓰는 카테고리
enum `[1,2,3,4,5,7]`과 정확히 일치)입니다. 이 필드로 다시 채점하자 0.5782로 나왔고, 논문(0.578)과
0.0002 차이로 사실상 일치했습니다 — "논문 수치에 맞을 때까지 필드를 바꿔본 것"이 아니라, "상수 필드는
채점 근거가 될 수 없다"는 데이터·코드 증거를 먼저 확보한 뒤 올바른 필드로 교체했고, 그 결과가 우연히도
논문과 거의 정확히 일치한 것입니다(선후관계를 분명히 하기 위해 기록).

**남은 불일치**: Global Spatial Error만 논문보다 +10.9% 높습니다(0.897 vs 0.809). Parts 레벨 3개 지표는
모두 0.1%p 이내로 일치하는데 Global Spatial Error만 차이가 남아 있어, 좌표축 슬라이싱(`position_pred
[:,1:]`)이나 벽/바닥 5-root 배치 기하 해석에 미세한 차이가 있을 가능성을 배제할 수 없지만, 확정하지
못했으므로 **"해석 필요/확인 불가"**로 남깁니다 — 임의로 보정하지 않았습니다.

## 10. 결론

환경 구축 이슈 6건(①~⑥, 패키지 버전) + 추가 소스 버그 3건(⑦~⑨, headless 실행 경로 한정 최소 패치)을
해결하고, **URDFormer 파이프라인(GroundingDINO 자동 탐지 조건)을 논문의 캐비닛류 카테고리에서 끝까지
성공적으로 재현**했습니다(정성적 검증 기준). §3에서 자동 탐지로 진행한 근거를 "논문 방법론에 더
가깝다"고 정당화했었으나, 이는 §3 말미에서 정정한 대로 **과장된 결론이었고 원본 LaTeX 소스 확인 후
철회**합니다 — 정확히는 "논문이 실제로 테스트한 두 조건(수동 라벨링 vs 자동 탐지) 중 하나를 재현한
것"이며, 어느 쪽이 "더 논문에 충실한가"라는 우열은 없습니다. **논문의 정량 지표는 "재현 불가능"이
아니라 채점 로직을 직접 구현하면 재현 가능함을 실측으로 증명**했습니다. §9에서 Object-Level 5개
카테고리 전체(300장, 논문과 동일 모집단)로 확장하고, GT박스 조건뿐 아니라 자동탐지(GroundingDINO)
조건까지 신규 구현·실행했으며, 사용자 지시로 Parent Accuracy 불일치를 정밀 재검증한 결과 **자동탐지
조건에서 실제 인덱스 매핑 버그를 발견·수정**했습니다(§9-3, 0.5394→0.9180). 수정 후 **8개 지표 중
6개(양쪽 조건의 Mesh Acc·Spatial Err, 자동탐지의 Recall·Precision)가 논문과 오차 1~2%p 수준으로 근접
일치**합니다. 다만 **Parent Accuracy는 두 조건 모두에서 논문보다 비슷한 폭(+9~11%p)으로 일관되게 높은
잔여 차이가 남아있고**, root/non-root 분리 검증까지 포함해 추가 원인을 찾았으나 확정하지 못해 §9-3에
정직하게 미해결로 기록했습니다 — 논문 수치에 맞추기 위해 억지로 조정하지 않았습니다.

노트북 힌지·로봇팔은 **논문의 학습 범주를 완전히 벗어나 있어 이 논문으로는 재현할 수 없음을 실제로
확인**했습니다(§6) — 이 부분은 애초에 저희가 메일에서 말씀드렸던 대로 **PhysX-3D 쪽에서 다뤄야 하는
영역**이라는 판단이 실측으로도 뒷받침됐습니다.

Kitchen 54씬(§9-5)도 GT박스 조건으로 전체 실행을 완료했고, 8개 지표 중 7개가 논문과 0.1%p 이내로
일치했습니다. 최종 판정은 §14 참고.

## 15. Kitchen Global Spatial Error 원인 추적 (임의 수정 없음)

**논문 수치**: 0.809 (Kitchen, GT boxes, Global, Spatial Error, "Ours")
**현재 재현 수치**: 0.8971 (54 scenes, n=486 objects) — 차이 +0.088(+8.8%p, 상대 오차 +10.9%)

### 15-1. 확인된 사실(코드/데이터로 직접 확인, 추측 아님)

- `evaluate.py`는 Global 레벨 position 예측(`position_pred_global`)을 **슬라이싱 없이 3축(x,y,z) 전체를
  그대로** 사용합니다(`root_position = position_pred_global[mesh_id] + np.array([1.2, 0.2, 0])` 등,
  3곳 전부 동일 — `grep -n "position_pred_global\["`로 직접 확인). 반면 Part 레벨 예측은 evaluate.py
  자체에서 **명시적으로 `[:, 1:]`(0번축 제외) 슬라이싱**을 적용합니다
  (`position_pred_end_parts.append(np.array(position_pred_end_part[:, 1:]))`).
- 반면 Kitchen GT의 `positions_start`/`positions_end`(Global 레벨)는 **2개 값만 저장**되어 있습니다(object당
  (10,2) — 전수 확인).
- 즉 **"예측 3축 중 어느 2축을 GT 2값과 비교해야 하는가"에 대한 공식 코드상 전례가 Global 레벨에는
  없습니다** — evaluate.py 자체가 이 비교를 한 번도 수행하지 않기 때문(§7에서 이미 확인한 "공식
  evaluate.py에는 채점 로직이 없다"는 사실의 연장선). 저희는 Part 레벨의 명시적 관행(0번축 제외)을
  유추해 Global에도 그대로 적용했습니다 — 이는 **"근거가 있는 가정"이지 "논문/코드가 명시한 사실"은
  아님**을 분명히 합니다.

### 15-2. 진단 1 — 축 선택 민감도 (가설 기각됨)

"혹시 축을 잘못 골랐나?"를 확인하기 위해, 3가지 조합(0번축 제외/현재 방식, 1번축 제외, 2번축 제외)으로
동일한 54 scene 전체를 다시 계산해 봤습니다(`diagnose_global_spatial.py`, 실제 채점 스크립트는
미변경):

| 조합 | Spatial Error |
|---|---:|
| **0번축(x) 제외 — 현재 방식** | **0.8971** |
| 1번축(y) 제외 | 1.5103 |
| 2번축(z) 제외 | 2.6734 |
| 논문 | 0.809 |

추가로 예측 3축 각각이 GT 2개 열 중 더 가까운 쪽과 얼마나 차이나는지(축별 최적 정렬 오차)도 계산:
x축 1.343, y축 1.065, **z축 0.117**(GT와 가장 잘 맞음). 즉 **현재 선택(x 제외, y·z 사용)이 시도해본

난다"는 가설은 **데이터로 기각됩니다**(오히려 현재 선택이 최선입니다). 이 진단은 사실을 확인하기 위한
것이었고, 결과와 무관하게 `score_kitchen.py`는 수정하지 않았습니다.

### 15-3. 진단 2 — 집계 방식(micro vs macro average) 민감도 (부분 설명, 미확정)

논문은 "54개 scene을 어떻게 합산하는지"(전체 object를 한 번에 pool해서 평균 낼지, scene별 평균의

| 집계 방식 | Spatial Error | 논문과 차이 |
|---|---:|---:|
| micro-average(전체 486개 object pool, **현재 방식**) | 0.8971 | +10.9% |
| macro-average(54개 scene별 평균의 평균) | 0.8454 | +4.5% |
| 논문 | 0.809 | — |

macro-average가 논문에 더 가깝지만(+10.9%→+4.5%), **완전히 일치하지는 않습니다** — 집계 방식 차이가
전체 격차의 절반 정도를 설명할 수는 있으나 전부는 아닙니다. 논문 원문(§Evaluation Metrics 문단)에
집계 방식이 명시되어 있지 않으므로, 이 역시 "해석 필요" 항목으로 남기고 **채점 스크립트의 기본값(micro-
average, pool 방식)은 변경하지 않았습니다** — 특정 집계 방식이 논문에 더 가깝다는 이유만으로 그것을
"정답"으로 채택하는 것은 사용자 지시("논문 수치에 맞추기 위한 임의 수정 금지")에 위배되기 때문입니다.

### 15-4. 결론 — 확인된 것 vs 가설 vs 미확인

| 구분 | 내용 |
|---|---|
| **확인된 사실** | evaluate.py는 Global 레벨에서 position 슬라이싱 전례가 없음(Part 레벨과 다름) — 축 선택은 원작자 코드가 아니라 저희의 유추 |

`score_kitchen.py`의 실제 출력(0.8971, micro-average, 현재 축 선택)은 **변경하지 않았습니다** — 이

## 18. Part 8 — 최종 재현성 판정: A(실행 성공) / B(프로토콜 재현) / C(정량 결과 재현) 구분

### A. 코드 실행 자체가 성공했는가

✅ **예.** 설치(§1), 추론(§3/§5), URDF 생성(§5), PyBullet 헤드리스 렌더링(§4) 전부 성공. Object-Level
300장(GT bbox+자동탐지 두 조건) 전량 skip 0/error 0. Kitchen 54 scenes(GT bbox 조건) 전량 skip 0/error 0.
Kitchen 자동탐지 조건은 "실행해서 실패"가 아니라 **애초에 실행하지 않음**(범위 밖) — 이 부분만 "확인 불가".

### B. 논문의 평가 프로토콜을 동일하게 재현했는가

🟡 **대체로 예, 단 논문이 명시하지 않은 부분에 대한 해석/가정 3건을 공개**:
- IoU 기반 Hungarian matching(§Evaluation Metrics 원문 그대로) 구현 — 자동탐지 조건에 적용, GT bbox
  조건은 정의상 불필요(박스 자체가 정답)함을 원문으로 확인.
- category/parent accuracy, handle·knob 중심점-only spatial 예외, Global/Parts 분리 — 전부 논문 원문
  문장을 근거로 구현(§Evaluation Metrics 직접 인용).
- **해석/가정 3건(논문 미명시)**: (1) Hungarian 매칭 수락 기준(IoU>0, §16), (2) Global 레벨 position
  예측 3축 중 2축을 선택하는 기준(§15-1, evaluate.py에 전례 없음), (3) 다중 scene 결과 집계 방식
  (micro vs macro average, §15-3, 논문 미명시). 세 가지 모두 **버그가 아니라 논문이 정의하지 않은
  영역에 대한, 근거를 남긴 선택**입니다.

### C. 논문의 정량 결과를 재현했는가

🟡 **부분적으로 예** — §17-2 종합표 기준 비교 가능한 14개 비-자명 지표 중 9개(64%)는 2%p 이내 근접,
2개는 경계, **3개(Object-Level GT/자동탐지 Parent Accuracy, Kitchen Global Spatial Error)는 8~11%p의
원인 미확정 잔여 차이**가 있습니다. 이 3개는 §9-3·§15에서 코드/데이터 수준으로 깊이 조사했으나 근본
원인을 확정하지 못했습니다 — **"논문과 다르다"는 이유만으로 구현 오류라고 판단하지 않았고**(실제로
찾아보니 그중 1건은 진짜 버그였고 수정했으나, 남은 3건은 재검증해도 버그를 찾지 못함), 반대로 **9개가
일치한다는 이유만으로 전체를 "재현 성공"이라고 판단하지도 않았습니다**(잔여 3건을 숨기지 않고 그대로
보고).

### 최종 판정

| 항목 | 판정 |
|---|---|
| A. 코드 실행 성공 | ✅ **성공** (Kitchen 자동탐지만 미착수, 확인 불가) |
| B. 평가 프로토콜 재현 | 🟡 **대체로 재현**(해석 필요 3건 공개) |
| C. 정량 결과 재현 | 🟡 **부분 재현**(14개 중 9~11개 근접, 3개 미확정 잔여차이) |
| **종합 판정** | **부분 재현(Partial Reproduction)** |

**"완전 재현" 아님, "재현 실패"도 아님 — "부분 재현"입니다.** 완전 재현으로 판정할 수 없는 구체적 이유:
(1) Object-Level Parent Accuracy 2건(GT bbox +10.9%p, 자동탐지 +9.2%p) 원인 미확정, (2) Kitchen Global
Spatial Error(+8.8%p, 상대 +10.9%) 원인 미확정(§15에서 축 선택 가설은 기각, 집계 방식 가설은 절반만
설명), (3) Kitchen 자동탐지 조건 미착수, (4) 논문 Figure와 동일 이미지 대 이미지 비교 미실시(§11).
재현 실패로 판정하지 않는 이유: 코드 실행은 전 구간(Kitchen 자동탐지 제외) 100% 성공했고, 14개 비교
가능 지표 중 64~79%가 논문과 2%p 이내로 근접하며, 평가 프로토콜의 핵심 요소(Hungarian matching,
category/parent/spatial 정의, Global/Parts 분리)는 논문 원문에 직접 근거해 정확히 구현했음을 코드
레벨로 확인했기 때문입니다.
