## 2. Object-Level Parent Accuracy — "불일치"가 아니라 비교 대상을 잘못 골랐던 것

**1차(0917) 시점**: 팀원(B)이 "[B의] Parent Acc(0.9833)가 논문(0.874)은 물론 [A의] 버그 수정 후 값
(0.9180)보다도 높다"고 불일치로 보고함(원문은 07 문서 자체 표현대로 "팀원"="A"을 가리키는데, 여기
서는 혼동을 피하려 누구를 가리키는지 대괄호로 명시함).

**연구원A의 반응**: 이 시점에 `수현/08_팀원_교차검증_회신_분석.md`를 작성해 직접 확인했다 —
0.9180은 연구원A의 GT-bbox 조건 값이 아니라 **자동탐지(Finetuned GroundingDINO) 조건** 값이었다
(원본 로그 `logs/44_autodetect_all5_FIXED_*.log`: `Parent Accuracy (matched only): 0.9180`).
연구원A의 실제 GT-bbox Parent Accuracy는 **0.9833**이고, 이 값은 팀원의 0.9833과 완전히 일치한다.

**2차(0920) 회신에서 팀원(B)도 동일 결론에 도달**: "0.9180은 [A의] GT-bbox 조건 값이 아니라 자동탐지
조건 값이었다"고 정확히 같은 원인을 짚었다 — 연구원A와 연구원B가 **서로 독립적으로 같은 오류를
발견**한 셈이다.

**최종**:

| | 연구원A | 연구원B | 논문 |
|---|---:|---:|---:|
| Parent Acc(GT-bbox) | 0.9833 | 0.9833(1354/1377) | 0.874 |

분모(1354/1377)까지 정확히 일치. 논문(0.874)과의 차이는 여전히 남아있지만, 이건 "연구원A와 연구원B가
서로 다르다"는 문제가 아니라 **둘 다 공통으로 겪는, 원인 미확인 별개 항목**이다(연구원A는 이전에
`환경구축_컴파일이슈해결/실행결과_보고.md` §9-3에서 root/non-root 분리 검증까지 했으나 원인

**배운 것**: 팀원이 조건(GT-bbox/자동탐지)을 명시하지 않고 숫자만 보내면, 연구원A가 임의로 조건을
가정하고 비교하는 실수가 생길 수 있다. 앞으로는 조건을 먼저 확인하고 비교하기로 함(양쪽 문서에

## 3. Object-Level Spatial Error — 연구원A는 처음부터 맞았고, 연구원B의 새 스크립트에서만 문제였다

> **(정정 이력)** 이 절은 최초 작성 시 연구원A와 연구원B의 값을 서로 바꿔 적는 오류가 있었다.
> 아래는 연구원A의 원본 로그(`logs/41_score_all5_gtbox_*.log`: `Spatial Error: 0.4759`)를 다시
> 직접 재확인해 바로잡은 내용이다.

**사실관계**: 연구원A는 이 지표를 처음부터 **0.4759**로 갖고 있었다(`score_object_level.py`, 300장
평가, 논문 0.478과 이미 근접). 연구원B는 이번에 Object-Level 300장을 처음 평가하며 완전히 새로운
스크립트(`evaluate_object_metrics.py`)를 작성했는데, **초기 결과가 0.7771**로 나와 논문(0.478)·
연구원A(0.4759) 양쪽과 불일치였다.

**원인**: 연구원A 자신의 `score_object_level.py` 141~147행에 이미 있는 논문 규정("handle=mesh id 4,
knob=mesh id 5는 중심점 2값만 비교, 그 외는 4값")이, 연구원B가 새로 작성한
`evaluate_object_metrics.py`에는 빠져있었다. (2026-09-17 시점 연구원A가
`수현/08_팀원_교차검증_회신_분석.md`에서 이 가능성을 먼저 지적했다.)

**2차(0920) 회신**: 정확히 이 가설대로였다 — 연구원B가 handle/knob 예외 처리를 추가해 재계산한
결과 **0.7771 → 0.4447**으로 바뀌어 논문(0.478)·연구원A의 값(0.4759)과 거의 완전히 일치했다.

**최종**:

| | 논문 | 연구원A(변동 없음) | 연구원B(수정 전) | 연구원B(수정 후) |
|---|---:|---:|---:|---:|
| Spatial Err | 0.478 | 0.4759 | 0.7771 | 0.4447 |

**(2026-09-20 코드 레벨 검증 완료)** `code_diff_evaluate_object_metrics_new_file.patch`를 실제로
전달받아 직접 열어 확인했다: mesh id 4(handle)·5(knob)는 `position_start`만(중심점 2값), 그 외는
`position_start`+`position_end`(4값)를 비교하는 코드가 정확히 서술한 그대로 구현돼 있었다(패치
115~128행). 함께 받은 원본 결과 파일 `object_metrics_result.json`을 직접 열어 재계산해보니
`spatial_err_4val_uniform: 0.7770515613652869`(≈0.7771), `spatial_err_handle_knob_exception:
0.44473684210526315`(≈0.4447)로, 서술된 수치와 정확히 일치했다. 원본 로그
`evaluate_object_metrics_run2.log`에도 `Mesh(Part) Acc: 1242/1377`, `Parent Acc: 1354/1377`,
`cabinets 100/100, ovens 50/50, dishwashers 50/50, fridges 50/50, washers 50/50`(총 300/300 성공)
이 그대로 찍혀 있어, 08번 문서의 서술이 전부 실제 코드·데이터와 일치함을 확인했다. 더 이상
"서술만 신뢰"가 아니라 **코드·원본 데이터로 독립 재검증 완료**.

## 5. Kitchen Parts Spatial Error — 연구원A는 이미 논문과 거의 일치, 문제는 연구원B의 스크립트

> **(정정 이력)** 이 절도 최초 작성 시 연구원A와 연구원B의 값을 서로 바꿔 적는 오류가 있었다.
> 연구원A 자신의 원본 로그(`logs/48_kitchen_all54_fixed_*.log`: `[Parts] ... Spatial Err=1.8001`)를
> 다시 직접 재확인해 바로잡았다 — **1.8001은 연구원B가 아니라 연구원A 본인의 값이다.**

| 계산 방식 | 값 |
|---|---:|
| **연구원A(`score_kitchen.py`, 54/54 scene, 변동 없음)** | **1.8001** |
| 논문 Table II(Kitchen, GT boxes, Parts) | 1.799 |
| 연구원B(3열 전부 사용, `evaluate_metrics.py` 최초) | 1.4575 |
| 연구원B(0번째 padding 열 제외) | 2.1863 |
| 연구원B(패딩 열 제외 + handle/knob 중심점 예외, 0920 신규) | 2.0409 |

**중요한 재해석**: 연구원A의 값(1.8001)은 논문(1.799)과 **차이가 0.0011밖에 안 되는, 사실상 완전
일치**다 — 이 지표는 처음부터 문제가 없었다. 실제로 재현이 안 되고 있는 쪽은 **연구원B의 별도
스크립트(`evaluate_metrics.py`)**이며, 세 가지 방식(3열 전부/패딩 제외/패딩 제외+handle·knob
예외)을 전부 시도했지만 어느 쪽도 논문이나 연구원A의 값에 도달하지 못했다.

**경위(연구원B 문서 기준)**: 연구원A가 0917에 "kitchen의 `part_positions_start`/`end` 0번째 열이
항상 0인 padding 열"이라는 사실(362개 파트/10개 장면 전수 확인)을 알려주며, 연구원B가 이 열을
빼면 자신의 값이 연구원A의 1.8001에 가까워질 것으로 예상했다. 실제로 빼보니 1.4575 → 2.1863으로
오히려 더 멀어졌고(반증), Object-Level에서 효과가 있었던 handle/knob 예외를 추가로 적용해도(0920,
2.1863→2.0409) 여전히 논문·연구원A 값보다 뚜렷이 높다.

**현재 판단**: Object-Level에서는 연구원B의 handle/knob 예외 추가만으로 거의 완전히 해소됐던 것과
달리, Kitchen에서는 그렇지 않다 — **연구원B의 `evaluate_metrics.py`에는 패딩 열·크기별 예외 외에
아직 밝혀내지 못한 세 번째 차이 요인이 남아있는 것으로 판단**한다. 연구원A의 `score_kitchen.py`
자체는 이 지표를 포함한 Kitchen 6개 지표 전부가 논문과 거의 완전히 일치하므로(§8 참고) 신뢰할
만하다 — **연구원A 쪽을 고칠 필요는 없어 보이며, 다음 교차검증에서는 연구원B의 kitchen Spatial
Error 계산 코드(`code_diff_evaluate_metrics_new_file.patch`)와 연구원A의 `score_kitchen.py`를
직접 나란히 놓고 좌표 조합·단위를 한 줄씩 대조하는 것이 필요**하다 — **확인 불가로 남기며, 억지로
논문/연구원A 수치에 맞추는 보정은 하지 않는다.**

**수령 파일 무결성 확인**: 연구원B가 09번 문서에 남긴 SHA256 해시 4개를 실제 파일에 대해
`sha256sum`으로 직접 재계산해 **전부 정확히 일치**함을 확인했다(52ab669b.../7a36ca40.../
7141e4e9.../cdac2e26...). 파일 크기(3,132 / 10,127 / 54,824 / 1,669 bytes)도 09번 문서 서술과
정확히 일치. 지어낸 값이 아니라 실제 파일 메타데이터임을 1차 소스로 확인했다.

**내용 검증 결과**: §3·§4에 반영한 대로, 두 patch 파일의 실제 코드가 07/08 문서의 서술과 정확히
일치함을 확인했고, `object_metrics_result.json`/`evaluate_object_metrics_run2.log`의 실제 수치도
서술된 값과 정확히 일치함을 확인했다. **더 이상 "서술만 신뢰"가 아니라 코드·원본 데이터 양쪽으로
독립 재검증을 완료한 상태다.** 받은 파일 5개는 이 저장소 `연구원B_검증자료/`에 원문 그대로
보존했다.

**여전히 남은 것**: Object-Level 자동탐지 교차검증용 2개(`labels_filtered_auto/` 폴더,
`score_object_level_autodetect.py`)는 이번에도 받지 못했다 — 애초에 patch가 아니라 아직 한 번도
전달된 적 없는 항목이며, 연구원B의 09번 문서 §2도 이를 "계속 대기 중"이라고 재확인했다(§7 참고).

## 8. 현재 시점 종합

| 지표 | 상태 |
|---|---|
| Object-Level Mesh Acc | ✅ 처음부터 일치(3자 일치) |
| Object-Level Parent Acc | ✅ 비교 오류 해소, 완전 일치(연구원A·연구원B) — 논문과의 차이는 별개 미해결 |
| Object-Level Spatial Err | ✅ 연구원A는 처음부터 근접(0.4759), 연구원B 신규 스크립트의 원인(handle/knob 예외 누락) 규명·수정 후 일치 — **코드·데이터 레벨 검증 완료(§6)** |
| Kitchen Global/Parts Mesh·Parent Acc | ✅ 처음부터 논문과 거의 완전 일치(연구원A 단독 산출, 변동 없음) |

| Object-Level 자동탐지 교차검증 | ⬜ 파일 대기 중, 미착수(변동 없음) |

**정리**: 연구원A 자신의 정량 지표(Kitchen 6개 + Object-Level 3개, 총 9개)는 이번 재검증 결과 **전부
논문과 거의 완전히 일치하거나(7개) 근접(1개), 계산 불가로 이미 판정된 것(1개)**으로 확인됐다 —
연구원A 쪽에서 추가로 고쳐야 할 지표는 없다. 남은 실질적 불일치는 **연구원B의 별도 스크립트
(kitchen용 `evaluate_metrics.py`)가 Kitchen Parts Spatial Error를 재현하지 못하는 것 하나뿐**이며,
이건 연구원A의 재현이 아니라 연구원B의 재현 쪽 과제다. 이번 라운드의 가장 중요한 교훈은 **"불일치처럼
보이는 것의 상당수가 실제 재현의 문제가 아니라 비교 방법(조건 미확인, 예외 처리 누락, 그리고 이번에
발견한 자기 자신의 A/B 값 전도 실수)의 문제였다"**는 것이다 — 처음엔 "서술만으로 받아들인 부분"으로
남겼던 §3·§4의 근거도, 요청한 patch/데이터 파일을 실제로 받아 SHA256 해시·코드 내용·원본 수치까지
전부 직접 대조해 **코드·데이터 레벨 검증을 완료**했다(§6).

> **재현 신뢰성 참고**: 이 문서 자체도 최초 작성 시 §3·§5에서 연구원A·연구원B의 수치를 서로 바꿔
> 적는 오류를 냈었다(원본 로그 재대조로 자체 발견·수정, 위 각 절의 정정 이력 참고) — "팀원 회신의
