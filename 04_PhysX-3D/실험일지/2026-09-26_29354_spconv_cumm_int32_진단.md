# 29354 pretrained inference spconv/cumm int32 진단

## 관찰된 실패

재실행 없이 기존 로그만 읽었다. `logs/inference-29354-run/20260925T191900Z/example.stderr.log`에서 실패 지점은 `decoder_mesh.py`의 sparse decoder가 `conv_spconv.py`를 통해 `spconv.pytorch`의 `indice_subm_conv`를 호출한 곳이다. 입력 feature는 `N=2,168,704`, `C=512`, fp16이며, 오류의 검사식은 `N*C*bits/8 < int_max`이다. 계산값은 `2,220,752,896` bytes로 `2^31-1`보다 `73,269,249` 초과한다. 따라서 직접 원인은 현재 cumm GEMM 경로의 int32 크기 제한이며, 로그에 좌표 값이 범위를 벗어났다는 증거는 없다.

## 현재 설치

`envs/physxgen`은 Python 3.10, `torch 2.7.1+cu128`(runtime CUDA 12.8), `spconv-cu126 2.3.8`, `cumm-cu126 0.7.11`이다. 실제 import 경로는 `site-packages/spconv`와 `site-packages/cumm`이다. dist-info의 wheel은 각각 `spconv_cu126-2.3.8-cp310-cp310-manylinux_2_28_x86_64.whl`(sha256 `16f3744cd697e225b1d6a9f37fd2a4aed7bd6b89dd4c431af5a76c39fda0ab38`)와 `cumm_cu126-0.7.11-cp310-cp310-manylinux_2_28_x86_64.whl`(sha256 `97a07c38b45d552952a12fd16f7f570f35b108e88068ed86386686bbbadaa59c`)이며 PHYSx 내부 cache에서 설치된 기록이 있다. spconv 메타데이터는 cumm-cu126 `>=0.7.11,<0.8.0`을 요구한다.

## 원본 코드 대조

고정 source README는 `setup.sh ... --spconv` 설치만 지정하고 별도 버전을 고정하지 않는다. `example.py`는 `SPCONV_ALGO=native`를 강제한다. 원본 sparse wrapper는 native면 `spconv.ConvAlgo.Native`, implicit_gemm이면 `MaskImplicitGemm`을 선택한다. 이번 오류는 conditioning PNG의 해상도보다 모델 decoder가 만든 2,168,704-point × 512-channel activation에서 발생했다.

## 원인 구분

- **확인됨: cumm/spconv 크기 제한.** 동일 오류 문구가 upstream spconv issue #706에 보고되어 있고, issue 본문도 voxel resolution·batch size가 큰지 확인하라고 안내한다.
- **가능한 기여 요인: CUDA wheel 불일치.** torch는 cu128인데 spconv/cumm은 공식 cu126 prebuilt다. CUDA minor compatibility로 즉시 원인이라고 단정할 수는 없지만, RTX 5090 sm_120용 native kernel이 없는 cu126 wheel이 PTX JIT 경로를 사용한다.
- **확인되지 않음: 입력 좌표 생성 버그.** 로그의 `pair`, `pairnum`, `feat`는 큰 activation을 보여주지만 좌표 유효성 실패는 없다.
- **확인되지 않음: RTX 5090 자체 문제.** 오류는 GPU 아키텍처 오류나 no-kernel-image가 아니라 cumm의 host-side 크기 assert다.

## 해결책 비교(설치하지 않음)

1. **가장 근거 있는 방향: CUDA 12.8/Blackwell용 spconv+cumm 쌍을 별도 환경에서 검증.** PyPI에는 `cumm-cu128 0.8.2` cp310 manylinux wheel이 있지만, upstream spconv 2.3.8은 cumm `<0.8.0`을 요구하고 공식 `spconv-cu128` wheel은 없다. 따라서 cumm만 교체하면 의존성·ABI가 깨질 수 있다. 기존 두 wheel과 torch를 보존한 별도 venv/복제 환경에서 cu128 쌍을 검증해야 한다.
2. **커뮤니티 cu128 wheel 쌍:** spconv 2.3.8+cumm 0.8.2의 sm_120 빌드가 있으나 upstream 공식 릴리스가 아니다. wheel 출처·hash·torch import 순서·ABI를 별도 검증해야 하며, 현재 환경을 직접 교체하면 되돌림 비용이 크다.
3. **알고리즘/입력 크기 회피:** `implicit_gemm`, 해상도·batch·activation 축소는 assert를 피할 가능성이 있지만 공식 example의 모델 동작과 입력 조건을 바꾸므로 논문 재현 해결책으로 간주할 수 없다. source 수정 없이 시험하려면 별도 wrapper가 필요하고 결과 비교가 필수다.
4. **torch 교체:** 공식 cu128 torch 2.7.1 wheel은 이미 현재 설치와 일치한다. 이번 오류만으로 torch 교체 근거는 없다.

근거 링크: [spconv issue #706](https://github.com/traveller59/spconv/issues/706), [spconv changelog](https://github.com/traveller59/spconv/blob/master/CHANGELOG.md), [upstream spconv setup dependency](https://github.com/traveller59/spconv/blob/master/setup.py), [cumm-cu128 0.8.2 wheel metadata](https://pypi.org/project/cumm-cu128/0.8.2/), [PyTorch cu128 wheel index](https://download.pytorch.org/whl/cu128/torch/). 커뮤니티 cu128 wheel은 [별도 저장소](https://github.com/fafraob/spconv-wheels)로 구분해 기록했다.

이번 진단에서는 설치·삭제·GPU 실행·example 재실행을 하지 않았다. 다음 설치 전에 확인할 사항은 (a) 새 환경에서 cu128 spconv와 cumm의 동일 ABI 쌍, (b) cumm 0.8.x와 spconv 2.3.8의 dependency pin 충돌을 해결하는 공식 근거, (c) sm_120 native kernel 또는 NVRTC 경로, (d) 현재 wheel cache와 정확한 rollback manifest다.
