## spconv/cumm 실제 파일과 GPU 결과

wheel 내부 cumm은 NVRTC12.6.85·cudart12.6.68을 번들하고 RPATH/DT_NEEDED로 연결한다. Toolkit PATH 선택만으로 번들 NVRTC가 12.8로 바뀌지 않는다. spconv에는 sm_52/sm_90 PTX가 있고 sm_120 cubin은 없었다. 정적 검사 후 실제 forward를 시험했다.

- 호스트 GPU1, minor1, UUID `GPU-843dced4-ee97-dbb8-36c9-343fe13b7647`, PCI02:00.0. 시작 전 호스트 계산 프로세스 목록이 비어 있었다. GPU0의 작업에는 접근하지 않았다.
- 격리 내부 GPU는 index0으로 재번호화됐다. UUID와 PCI를 호스트 값에 대조하고 `/dev/nvidia1`만 노출했다. 네트워크 차단, 환경/Toolkit 읽기 전용, 캐시/임시 파일 PHYSx 내부 조건을 유지했다.
- 18:06:45–18:07:03 KST, 작은 FP32 SubMConv3d 3×3, 8개 활성 voxel, 입력/출력 채널4. TF32 끔.
- native와 auto→MaskImplicitGemm 모두 CPU float64 dense conv3d 기준과 좌표를 정렬해 비교: 최대 절대 오차 **0**, NaN/Inf 없음, 종료0.
- 실행 중 실제 매핑에 cumm 번들 NVRTC12.6 및 PyTorch NVRTC12.8이 함께 존재했다. 라이브러리 이름만으로 어떤 커널 경로가 실행됐는지 단정하지 않는다.
- [GPU 표본 18개](../재현자료/2026-09-21_공식예제진행/01_sparse검사/gpu-samples.json)와 전/중/후 원본 기록을 보존했다. 표본은 연속적인 전체 최대값을 보장하지 않는다.

## 실패·원인·수정·재실행

1. 최초 격리 실행은 외부 도구 샌드박스의 bwrap namespace 생성 제한으로 중단됐다. 보호 설정을 변경하지 않고 승인된 외부 실행 안에서 동일 bwrap 제한을 유지했다.
2. 첫 GPU 실행기는 호스트 index1을 격리 내부에도 요구해 연산 시작 전 중단했다. 실제 조회가 같은 UUID/PCI의 내부 index0임을 확인했다. 호스트 index1과 내부 index0을 각각 검사하도록 수정했고, 위 sparse 재실행은 성공했다. UUID/PCI·단일 장치 확인을 제거하지 않았다.
3. FlashAttention2.8.3 첫 실제 빌드는 g++가 `cuda_runtime_api.h`를 찾지 못해 실패했다. Conda Toolkit의 실제 `targets/x86_64-linux/include`와 link용 `targets/x86_64-linux/lib`를 C/C++ include 및 `LIBRARY_PATH`로 명시했다. `LD_LIBRARY_PATH` 우회나 Toolkit 파일 변경은 하지 않았다. 수정 후 빌드는 진행 중이며 이 일지에서는 성공으로 판정하지 않는다.

## 명령과 다음 단계

재현 명령의 전체 argv, stdout/stderr, 종료코드는 증거의 `command.json`, `stdout.log`, `stderr.log`, `result.json`에 있다. 현재 실행기는 `workspace_runner.py --execute --profile install|build|gpu`이며 기본 실행은 계획 출력이다. 예전 검토용 설치 스크립트를 일괄 실행하지 않았다.

다음은 FlashAttention 빌드 완료, Kaolin·렌더러·attention 실제 연산 검사, 고정 가중치 준비 후 table 예제 한 개 실행이다. **이번 성공은 설치와 작은 sparse 연산까지이며 모델 실행·출력 검증·논문 정량 재현 성공이 아니다.** 큰 채널/FP16 sparse 경로와 NVRTC fallback은 아직 일반적으로 검증되지 않았다. 모델 다운로드도 진행 중이므로 완료 주장에 포함하지 않는다.
