# Spring-Gaus — 이수현은 재현 성공, 김승민은 재현에 성공하지 못함

**작성일**: 2026-09-14

| 항목 | 이수현 | 김승민 |
|---|---|---|
| torus (합성 데이터) | 완료(1시간 42분) | 재현 실패(4회 시도 — RUN 1·2·3·스모크 테스트 — 후 중단) |
| burger (실측 데이터) | 완료(약 12시간 54분) | 시도하지 못함(torus가 끝나지 않아 다음 단계로 넘어가지 못함) |

**원인 요약**: 두 사람이 쓴 코드·설정은 완전히 동일했고, 환경 조회 결과 실제로 다른 부분(GPU 드라이버,
확장 모듈 컴파일용 CUDA 버전, pytorch3d 버전) 3가지를 찾았습니다. 이 중 확장 모듈 컴파일용 CUDA
버전과 pytorch3d 버전은 소스 코드로 호출 위치를 직접 확인해 이 병목과 무관할 가능성이 높다고 판단했지만,
**GPU 드라이버 버전 차이는 성격상 코드 검토로 배제할 수 있는 항목이 아니라 이 방법으로는 검증하지
못했습니다.** 실측 근거가 있는 후보는 김승민 쪽에서 학습 내내 VRAM이 97%까지 근접해 있었다는 점인데,
이수현 쪽은 비교할 수치가 없어 확정하지 못했습니다. 추가로 PyTorch 공식 GitHub 이슈를 검색해보니
VRAM 압박보다는 "물리 계산 중 특정 순간 인덱스가 몰리는 현상"이 병목 연산의 backward를 느리게 만드는
더 구체적인 원인일 가능성도 있었지만, 이 역시 왜 한쪽 PC에서만 나타났는지는 설명하지 못합니다.
**결론적으로 단일 원인은 아직 특정하지 못했고**, 아래에 검증 과정을 상세히 남겨둡니다.

### 왜 이런 차이가 있었는지 — 상세 원인 분석 (추측이 아닌 환경 대조 + 코드 확인 결과)

김승민은 torus 학습 후반부(물리 서브스텝 수가 200으로 늘어나는 구간)에서 프레임 하나 처리에 최대
1시간 가까이 걸리는 극심한 지연을 4차례 시도 내내 겪었고, 끝내 완주하지 못했습니다. `torch.profiler`로
직접 원인을 추적한 결과, 원본 논문 코드 자체에 있는 성능 결함 2가지를 찾아냈습니다.

1. 물리 계산 루프 안에서 불필요하게 반복 호출되는 GPU 메모리 정리 함수
2. 특정 경계조건 계산의 역전파 연산이 비정상적으로 느려지는 문제

이 결함을 고쳐 격리된 벤치마크로 테스트하면 처리 시간이 최대 32.6배까지 단축됐지만, 이 수정을 실제
학습 전체에 적용해도 지연은 완전히 해소되지 않았습니다. 반면 이수현은 위 두 결함을 전혀 고치지 않은
원본 코드 그대로, 같은 사양(i7-9700K/64GB/RTX 2080 Ti 11GB)에서 torus를 정상적으로 완주했습니다
(n_step=200 구간만 놓고 보면 약 39분 만에 통과). 같은 코드·같은 사양인데 왜 이런 차이가 났는지, 추측이
아니라 두 PC의 환경을 실제로 조회하고 관련 소스 코드를 직접 읽어 확인했습니다.

**① 실제로 다른 부분이 있는지 확인한 결과 — 3가지 환경 차이 발견**

| 항목 | 이수현 | 김승민 |
|---|---|---|
| GPU 드라이버 버전 | 576.02 | 572.83 |
| diff-gaussian-rasterization·simple-knn 컴파일에 쓴 CUDA | conda 번들 CUDA 11.6(nvcc 11.6.124) | 별도 설치 CUDA 11.8(nvcc 11.8.89) |
| pytorch3d 버전 | 0.7.9(최신 main 커밋을 그대로 쓰되 C++17 컴파일 플래그를 고쳐서 해결) | 0.7.6(최신 커밋이 PyTorch 1.13과 안 맞아 의도적으로 구버전 커밋에 고정) |
| PyTorch 본체 | 1.13.1+cu116(공식 pip 휠) | 1.13.1+cu116(공식 pip 휠) — **완전히 동일** |

**② 위 차이들이 실제 원인일 수 있는지 소스 코드로 직접 검증**

- 병목 연산(`aten::_index_put_impl_`)은 `apply_bc`/`apply_bc_force` 안에 있고, 이 함수들은
  `Spring_Mass.py`의 `forward()`가 프레임마다 실행하는 `for _ in range(self.n_step): self.step(...)`
  반복문(n_step=200이면 프레임당 200번) 안에서 호출됩니다. 이 연산 자체는 PyTorch가 미리 컴파일해
  배포하는 공식 코드인데, **두 사람 다 완전히 동일한 버전의 공식 pip 휠(`torch==1.13.1+cu116`)을
  설치**했습니다 — 즉 이 연산의 실행 코드는 두 PC에서 한 글자도 다르지 않습니다.
- pytorch3d의 `knn_points`는 `Spring_Mass.py` 소스를 직접 읽어 확인한 결과, 모델을 처음 만들 때
  (`__init__`, `set_all_particle`) 딱 한 번만 호출되고, 문제의 반복문(`step`/`apply_bc`/
  `apply_bc_force`/`compute_force`) 안에서는 전혀 호출되지 않습니다. → 버전 차이는 실재하지만, 이
  병목의 직접 원인일 가능성은 낮습니다.
- diff-gaussian-rasterization(렌더링)도 `train.py`의 `render_step()`을 직접 읽어 확인한 결과 프레임당
  1번만 호출되고, n_step 반복문 안에서는 호출되지 않습니다. → 이를 컴파일한 nvcc 버전 차이도 이 특정
  병목의 직접 원인일 가능성은 낮습니다.
- **GPU 드라이버 버전(576.02 vs 572.83)은 위 두 항목과 성격이 다릅니다.** 드라이버는 특정 함수가 아니라
  모든 CUDA 연산을 실행할 때 전역적으로 관여하기 때문에, "어느 코드에서 호출되는지"로 배제하는 방식
  자체가 적용되지 않습니다. 즉 병목 연산(`aten::_index_put_impl_`)도 결국 드라이버를 거쳐 실행되므로,
  이 차이는 **원인일 가능성을 배제하지 못한 채로 남아 있습니다**(그렇다고 원인이라는 근거가 있는 것도
  아닙니다 — 3버전 차이는 비교적 작은 마이너 업데이트 폭이고, 어느 쪽 문서에도 드라이버 관련 이상
  징후가 보고된 적은 없습니다).

**③ 남는 후보 두 가지 — VRAM 여유 부족 / 인덱스 집중(concentration) 문제 (둘 다 미확정)**

김승민 쪽 문서에는 n_step=200 구간 내내 VRAM이 **10.9~11.0GB / 11.26GB(약 97%)**로 한계치에 붙어
있었다는 실측 기록이 있고, 이는 어떤 수정도 적용하기 전인 첫 시도(RUN 1)부터 이미 그랬습니다. 이
부분은 PyTorch 공식 자료로 "VRAM이 근접하면 캐싱 할당자가 단편화를 겪는다"는 일반적 사실까지는
확인했지만, 이게 `index_put_`의 backward를 100배 이상 느리게 만든다는 직접적 근거는 찾지 못했습니다.

대신 검색으로 더 정확히 들어맞는 후보를 하나 더 찾았습니다: PyTorch 공식 GitHub 이슈
([#74487](https://github.com/pytorch/pytorch/issues/74487),
[#128631](https://github.com/pytorch/pytorch/issues/128631))에 따르면 `scatter`/`index_put_` 계열
연산의 backward는 **인덱스 값이 중복되거나 한쪽에 몰려있을 때(concentrated/duplicated index)**
병적으로 느려지는 것으로 보고되어 있습니다. `apply_bc`가 만드는 인덱스(`v_index = torch.where(바닥에
닿은 조건)[0]`)는 물리 상태에 따라 그 순간 얼마나 많은 입자가 한꺼번에 바닥에 닿는지에 좌우되는 값이라,
이 메커니즘이 VRAM 압박보다 더 그럴듯한 설명일 수 있습니다. 다만 이 역시 확정은 아닙니다 — 같은
코드·같은 설정이면 물리 시뮬레이션도 이론적으로 동일하게 진행돼야 하는데, 왜 한쪽 PC에서만 이런
상태가 나타났는지는(부동소수점 연산 순서가 하드웨어마다 미세하게 달라 궤적이 아주 조금씩 벌어졌을
가능성 정도가 추정 가능하나, 이 역시 확인된 사실은 아님) 설명되지 않습니다.

다만 이수현 쪽 torus는 하나의 백그라운드 작업으로 시작해서 약 1시간 42분 뒤 완료 알림이 올 때까지
문제없이 진행되어, 중간에 GPU 상태를 따로 확인할 계기가 없었습니다(burger는 소요 시간이 훨씬 길고
그 사이 진행 상황을 계속 확인해야 했던 터라 GPU 사용률·VRAM을 여러 차례 기록해뒀지만, torus는 그럴
필요 자체가 없었습니다). 그래서 **이수현 쪽에는 torus 실행 당시의 VRAM 수치가 남아있지 않고**, 두
PC의 VRAM 여유분을 직접 비교하지는 못했습니다 — 확인되지 않은 사실로 남겨둡니다.

**④ 이수현 쪽에서 추가로 실측한 것 (2026-09-14, 학습을 돌리지 않은 평상시 상태)**

김승민 쪽에 요청한 것과 같은 항목을 이수현 쪽에서 먼저 재보았습니다(`nvidia-smi -q`). 아래 표는
최초 측정 당시의 실측값입니다(원본 파일은 내부 검토용으로 별도 보관, 이 저장소에는 포함하지 않음).

| 항목 | 이수현 (실측) |
|---|---|
| PCIe 링크 (현재 / 최대) | **Gen3 x8 / Gen3 x16** — x16 슬롯인데 절반(x8)으로만 연결됨 |
| idle 상태 VRAM 사용량 | 839 MiB / 11,264 MiB |
| idle 상태 GPU 사용률 | 36%(완전한 유휴 상태가 아니었음 — 다른 프로그램이 뭔가 쓰고 있었던 것으로 추정) |
| 드라이버 | 576.02 |

PCIe가 x8로 떨어져 있다는 건 이번에 처음 확인한 사실입니다. 다만 PCIe 대역폭은 주로 CPU↔GPU 데이터
전송에 영향을 주는 것이라, `index_put_`처럼 GPU 안에서만 도는 연산의 속도 자체를 직접 좌우할 가능성은
낮아 보입니다 — 그래도 "이수현 PC의 하드웨어 구성도 완벽한 최적 상태는 아니었다"는 점, 그리고 idle
상태가 완전히 0이 아니었다는 점은 사실로 남겨둡니다. 김승민 쪽 같은 항목은 이후 실제로 전달받아
아래 ⑤에서 나란히 비교했습니다.

**⑤ 김승민 쪽에서 받은 실측 데이터 (2026-09-14, 요청한 자료 전달받음)**

원본 로그 파일(RUN1·RUN2·RUN3 `.log` 그대로), `nvidia-smi -q` 전체 출력, 학습을 짧게 재현하면서 1초
간격으로 남긴 실시간 GPU 기록(`gpu_log.csv`)까지 전달받아 직접 확인했습니다.

- **원본 로그 검증**: `tr '\r' '\n'`으로 원본을 펼쳐서 n_step 전환 시각·프레임별 경과시간을 전부 다시
  대조한 결과, 기존 문서에 인용됐던 모든 수치(RUN1의 20:11:06/20:42:16 전환, RUN3의 "frame 0→1 전환
  20분46초" 등)가 원문과 **정확히 일치**했습니다. 추가로 발견된 오류는 없습니다.
- **PCIe**: Gen3 x8/x16 — 이수현 쪽과 **똑같이 x8로 떨어져 있음**. 즉 PCIe 상태는 두 PC가 동일해서,
  이 부분은 차이의 원인이 아닙니다.
- **진짜 idle 상태**: 처음 보내주신 "idle 체크" 두 파일은 사실 학습이 이미 시작된 뒤에 찍힌 것으로
  보여(82~95% 사용률, VRAM 96%) 진짜 idle이 아니었습니다. 대신 모든 테스트가 끝난 뒤 찍힌
  `gpu_spec_full.txt`(14:52:48)가 진짜 idle 상태를 보여줍니다: **VRAM 674MiB, GPU 7%** — 이수현의
  idle 값(839MiB, 36%)과 비슷한 수준입니다. **즉 두 PC의 평상시(대기) 상태는 비슷하고, 문제는 학습이
  시작된 뒤에만 나타납니다.**
- **오늘 새로 재현한 14.5분 기록**(`gpu_log.csv`): GPU 사용률 평균 91%(최저 23%~최고 100%), VRAM
  90~98%(10,191~10,999 MiB). 이 구간은 시간상 아직 n_step=200 이전(초반) 구간으로 추정되는데, **이미
  이 시점부터 VRAM이 거의 꽉 차 있었습니다.** 이수현 쪽은 같은 초반 구간의 VRAM을 측정해두지 않아 직접
  비교는 못 하지만, 방향성은 "VRAM 여유 부족" 가설을 조금 더 뒷받침합니다.

**⑥ 한 걸음 물러나 재점검 — 놓쳤던 가정과 새로운 통합 가설 (2026-09-14)**

"VRAM 부족이냐 인덱스 집중이냐"를 서로 다른 두 후보로 다루기 전에, 그동안 직접 확인 안 하고 넘어간
가정이 있는지부터 다시 점검했습니다.

- **랜덤 시드 직접 대조**: 김승민 원본 로그엔 `setup random seed : 123`이 찍혀 있는데, 이수현 쪽
  로그엔 이 줄이 아예 없었습니다. 시드가 다른가 의심해서 `train.py` 코드를 직접 읽어봤는데, 이
  로그 줄은 **로그 파일 핸들러가 생성되기 전(콘솔에만 출력되는 시점)**에 찍히는 것이었습니다. config의
  `SEED: 123`은 두 사람 다 수정하지 않은 동일 파일이므로, 실제 시드값 자체는 같다고 봐야 합니다. →
  **이건 시드 차이가 아니라 각자 로그를 파일로 담은 방식(콘솔 출력 리다이렉션 여부) 차이였습니다.**
  막다른 길이었지만 확인 안 했으면 몰랐을 부분입니다.
- 이 과정에서 **더 중요한 한계를 발견했습니다**: 이수현 쪽 torus 로그 파일에는 프레임별 loss 값이
  전혀 남아있지 않습니다(tqdm 진행률 텍스트가 파일에 안 담김, 총 124줄뿐). **그래서 "두 컴퓨터의
  물리 시뮬레이션 궤적이 실제로 똑같이 진행됐는지"를 직접 비교할 방법이 이수현 쪽 데이터 부재로
  원천적으로 없습니다.** 지금까지 "같은 시드니까 같은 계산이 나왔을 것"이라고 암묵적으로 가정했는데,
  이 가정 자체를 검증할 수 없는 상태였다는 것을 인정합니다.
- **파워 리밋도 직접 대조**: 두 GPU 모두 300W(최대 366W)로 동일 — 차이 아님.

**인과관계를 다시 생각해보면**: 지금까지 "VRAM 부족"과 "인덱스 집중"을 서로 다른 두 후보로 놓고
봤는데, 이 둘은 **독립적인 두 원인이 아니라 같은 사건의 서로 다른 증상일 가능성**이 있습니다.
`apply_bc`/`apply_bc_force`의 역전파가 비정상적으로 오래 걸리면, gradient checkpointing이 없는
이 코드 구조상 그동안 계산 그래프 전체가 메모리에 계속 붙잡혀 있어야 합니다 — 즉 **VRAM이 97%로
오래 붙어있는 현상은 원인이 아니라, 역전파가 느려진 것의 결과(증상)일 수 있습니다.**

그렇다면 왜 김승민 컴퓨터에서만 역전파가 느려지는 인덱스 패턴이 나타났는지가 남는데, 가장 정합적인
설명은 **GPU 결정성(determinism)의 한계**입니다. PyTorch의 `cudnn.deterministic=True`(이 코드에
기본 적용됨, 두 로그 모두 별다른 경고 없음)는 **같은 하드웨어+드라이버 조합 안에서의 재현성만
보장**하며, 서로 다른 GPU 드라이버 버전 간의 동일한 결과까지는 보장하지 않는다는 것이 PyTorch
자체의 공식적으로 알려진 한계입니다. 두 PC의 드라이버 버전이 다르므로(572.83 vs 576.02), 아주
미세한 부동소수점 차이가 날 수 있고, "바닥에 닿았는가"처럼 불연속적인 경계조건 판정에서는 이런
미세한 차이가 완전히 다른 입자 집합이 선택되는 결과로 갈릴 수 있습니다. 실제로 김승민은 RUN1·RUN2에서
**같은 지점에서 매번 동일하게** 멈췄는데, 이는 "같은 컴퓨터+같은 드라이버+같은 시드 = 매번 같은
결과"라는 것을 보여주는 정황이고, 이수현 컴퓨터는 드라이버가 달라 처음부터 미세하게 다른(문제없는)
계산 경로를 탔을 가능성과 부합합니다.

**이 가설의 한계(정직하게 표기)**: 이 설명은 지금까지 확인된 모든 사실과 모순되지 않는 가장 정합적인
이야기이지만, **직접 증명하지는 못했습니다.** 증명하려면 두 PC의 프레임별 loss 값을 나란히 비교해야
하는데, 위에서 확인했듯 이수현 쪽에 그 데이터 자체가 없습니다. 확정된 사실이 아니라 "현재 증거를
가장 잘 설명하는 가설"입니다.

**결론**: 문제의 연산 코드와 이를 호출하는 로직은 두 사람이 완전히 동일합니다(같은 커밋, 같은 공식
PyTorch 배포본, 같은 config의 SEED: 123). 확인된 환경 차이 중 nvcc(확장 모듈 컴파일용)·pytorch3d
버전·PCIe·파워 리밋은 코드 대조·직접 측정으로 이 병목과 무관함을 확인했습니다. **GPU 드라이버 버전
차이(572.83 vs 576.02)만 유일하게 배제되지 않은 채 남아 있으며**, "VRAM 97%"와 "인덱스 집중 backward
저하"는 서로 다른 두 원인이 아니라 **같은 근본 원인(드라이버 차이로 인한 부동소수점 궤적 발산 →
경계조건에서 다른 입자 집합 선택 → index_put_ backward 저하 → 그 결과로 VRAM이 오래 붙잡힘)의
증상들일 가능성이 가장 높다**고 판단합니다. 다만 이수현 쪽에 프레임별 loss 데이터가 없어 이 가설을
직접 증명하지는 못했고, **단일 원인은 여전히 확정하지 못한 상태입니다.**

이 원인 분석을 바탕으로 김승민은 다음 재현 시 (a) VRAM 여유 부족이 정말 원인인지 직접 검증하거나,
(b) VRAM이 더 넉넉한 GPU 환경에서 같은 실험을 재현해 VRAM 여유를 늘리면 문제가 사라지는지 확인하는
방향으로 다시 시도해볼 계획입니다. 다만 이수현도 같은 RTX 2080 Ti 11GB로 이미 성공했기 때문에,
"11GB 카드 자체의 한계"라기보다는 김승민의 개별 PC·환경에 국한된 문제일 가능성이 있습니다 — 즉 (b)는
원인을 밝히는 검증이라기보다 더 넉넉한 환경으로 우회해서 완주 자체를 시도해보는 성격에 가깝습니다.
(b)는 랩의 다른 GPU 자원 활용 여부가 걸려 있어 교수님 결정이 필요한 부분입니다.
