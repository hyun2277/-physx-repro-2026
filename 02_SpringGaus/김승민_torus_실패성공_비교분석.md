### 3-1. n_step=100·150 구간 — 모든 시도에서 일관되게 정상

아래 표의 "구간 페이스" 값은 각 구간이 끝나는 전환 시점(iteration 99, 199)에 tqdm이 표시한
누적 `s/it` 값을 그대로 인용한 것이다(RUN 1/2/3는 `07` 문서가 이미 이 값을 "n_step=150 구간 페이스"로
명명해 비교한 방식을 그대로 따름). tqdm이 순수 구간 평균인지 최근 구간에 가중치를 둔 평활값인지까지는
확인하지 않았으므로, 절대값보다는 **"이 구간에서도 초 단위였다"는 자릿수 비교** 용도로만 사용한다.

| # | 시도 | n_step=100 구간 페이스 | n_step=150 구간 페이스 |
|---|---|---|---|
| 1 | RUN 1 | (수치 미기록) | 12.74s/it |
| 2 | RUN 2 | (수치 미기록) | 12.78s/it |
| 3 | RUN 3 | (수치 미기록) | 13.15~13.22s/it("30% 개선") |

이 구간은 **실패 시도든 성공 시도든 전부 초 단위 페이스로 정상**이었다. `empty_cache` 패치가 있는
쪽(RUN3, #7)이 없는 쪽(RUN1, RUN2)보다 약간 더 빠른 정도의 차이만 있고, 자릿수가 달라지는 이상 현상은
이 구간에서 전혀 없었다. **문제는 항상 n_step=200 구간에서만 나타났다.**

확인할 수 있는 범위 안에서는, 이 두 구간 사이에 재부팅이 있었는지, 드라이버가 재시작됐는지, 다른
백그라운드 작업이 있었는지는 기록이 없어 확인할 수 없다.** 드라이버 버전 자체는 두 구간 모두 572.83으로
동일함이 확인됐으므로(§2-1), "드라이버가 바뀌었다"는 설명은 배제된다. 이 시간대 구분이 원인과 관련이
있는지, 단순 우연인지는 **미확정으로 남긴다.**

|---|---|---|

## 7. 결론

### 7-1. 확정된 사실

1. 완전히 동일한 코드·config·패치 상태·PC·드라이버에서, 실행 시점만 다르게 4번은 실패했고 3번은
   정상 진행했다(§2·§4).
2. 실패는 항상 n_step=200 구간에서만 나타났고, n_step=100·150 구간은 모든 시도에서 예외 없이
   정상이었다(§3-1).
3. 실패 시도의 "느린 프레임 1개" 소요 시간(20~64분)은 성공 시도의 "n_step=200 구간 전체(최대
   5,700프레임)" 소요 시간(약 25~80분)과 최소 같은 자릿수였고, 4건 중 3건(RUN 2, RUN 3의 두 번째
   프레임, 스모크 테스트)은 그 전체 구간 시간보다도 더 길었다 — 예를 들어 RUN 2의 프레임 1개(58분25초)가
   실제 커리큘럼 재확인의 n_step=200 구간 전체(24분53초)보다 길었다(§3-2, §3-3).
4. 지금까지 만든 두 가지 코드 수정(`empty_cache` 무력화, `apply_bc`의 `index_put_` 재작성)은 실측
   결과상 성공/실패를 가르는 변수가 아니었다(§2-2).

### 7-2. 아직 모르는 것

- 왜 같은 조건에서 실행 시점에 따라 결과가 갈리는지, 정확한 트리거는 특정하지 못했다(§6).
- 실패 구간(9/13 저녁~9/14 아침)과 성공 구간(9/14 오후 이후) 사이에 실제로 무엇이 달라졌는지는 확인할
  방법이 없다(§5) — 재부팅 여부, 백그라운드 프로세스, 열이력 전부 기록이 없어 "모른다"가 정직한
  답이다.
- 반복 시행 시 성공률이 몇 %인지는 표본이 너무 적어(성공 3, 실패 4) 통계적으로 말할 수 없다.

### 7-3. 실용적 함의

재현 가능 여부만 놓고 보면 torus는 **재현된다** — 원본 코드로 산출물(체크포인트·평가 영상)까지 나온
성공 사례가 있다. 다만 **매번 성공한다고 보장할 수는 없다.** 이후 이 코드베이스를 다시 돌릴 일이
있다면(팀원 공유, 다음 세션 등) 이 비결정성 자체를 미리 알려주는 것이 맞고, 실패하더라도 "코드가
잘못됐다"고 오판하지 않도록 이 문서를 함께 참조하게 하는 것이 좋다.
